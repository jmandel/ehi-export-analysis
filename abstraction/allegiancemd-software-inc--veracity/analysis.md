# EHI Export Analysis: AllegianceMD Software, Inc.

**Product**: Veracity v9.1
**Analysis date**: 2026-02-15
**CHPL ID**: 15.02.05.2672.ALLE.01.01.1.220117 (CHPL ID 10794)

## 1. Product Context

Veracity is a cloud-based, all-in-one EHR/practice management/billing platform targeting small-to-mid-sized ambulatory practices. It is explicitly marketed as an integrated system — not modular — encompassing:

- **Clinical EHR**: Charting, problem lists, medications, allergies, vitals, CPOE, drug interaction checking, clinical decision support, e-prescribing (including EPCS), clinical templates for 50+ specialties
- **Practice Management**: Appointment scheduling, patient registration, case management (workers' comp, etc.), document management, electronic faxing
- **Billing & Revenue Cycle**: Charge capture, claim creation/scrubbing/submission, eligibility verification, ERA/remittance posting, denial management, patient statements, collections, credit card processing
- **Patient Portal**: Demographics, secure messaging, appointment scheduling, refill requests, statement viewing, medical records access
- **Other**: Telemedicine, immunization registry reporting, MIPS/MACRA quality reporting, chronic care management (CCM), lab interface, annual wellness visits

For EHI export assessment, the key question is whether the export covers clinical data, billing/claims data, insurance data, case management data, portal messages, documents, and specialty-specific clinical content — all of which Veracity stores.

## 3. Export Mechanics

- **Format**: CBOR (Concise Binary Object Representation, RFC 8949) — a binary serialization format semantically equivalent to JSON but in compact binary encoding. Unusual for healthcare; more common in IoT/constrained environments.
- **Delivery**: ZIP file containing CBOR-encoded data objects, documents, clinical data files, and `.meta` files describing each document.
- **Mechanism**: Not documented. The documentation page provides no instructions on how to request or initiate an export. No UI screenshots, no API endpoint, no workflow description.
- **Single-patient vs bulk**: The data model is patient-centric (PatientEntity is the root), suggesting single-patient export. No mention of bulk/multi-patient capability.
- **Access constraints/fees**: Not documented in the artifacts. The CHPL mandatory disclosures PDF URL exists but was not collected.
- **Tooling**: The vendor points to https://cbor.io/impls.html for open-source CBOR libraries.

### Data architecture

The export uses a **hierarchical, patient-centric model**. `PatientEntity` is the root, with 20 `List<>` references to child entities. Additional nesting exists:
- `CasesEntity` → `InsuranceDataEntity` → `InsuranceDataAuthorizationsEntity`
- `EncountersEntity` → `EncountersDiagEntity`, `TransactionsEntity`
- `EmrPatientOrderPanelEntity` → `EmrPatientOrderItemEntity`
- `TasksEntity` → `TaskCommentsEntity`

Some entities (GuarantorEntity, PatientCareTeamEntity, EmrVitalsCategoryEntity, EmrEncounterEntity) are not directly referenced from PatientEntity via list fields but appear to be linked through foreign keys (e.g., `pid` fields).

Field types: String (427), Date (111), Boolean (84), Double (36), Integer (21), Short (8), Long (1), byte[] (1), plus 26 List<> references.

No value sets, code systems, or foreign key documentation are provided. No sample data files.

## 6. Documentation Quality

**Strengths:**
- The Javadoc format is navigable — each entity links to a field listing with types
- The 4 fully-documented entities (PatientEntity, CasesEntity, InsuranceDataEntity, InsuranceDataAuthorizationsEntity) serve as good examples: every field has a plain-English description
- The hierarchical entity model is well-expressed through `List<>` type annotations — relationships are clear
- Java data types (String, Integer, Boolean, Date, Double, Long) are consistently documented
- The data model is clearly a native database serialization, not a FHIR/C-CDA projection

**Weaknesses:**
- **77% of fields lack any description** — only field names and types. Many field names are self-explanatory (e.g., `firstName`, `lastName`, `dob`, `amount`), but others are cryptic (e.g., `pqrsQualDataCode`, `hcfa21_4`, `modifier1`, `tobaccoRecode`)
- **No value sets or code systems** — fields like `status`, `type`, `action` have String type but allowed values are unspecified. Diagnosis fields (`diag1`–`diag12`) don't indicate ICD-10 vs SNOMED
- **No sample data** — no example CBOR file, no example export ZIP
- **No user guide** — no instructions for requesting an export, no workflow documentation, no screenshots
- **No `.meta` file schema** — documents are claimed to be included with `.meta` description files, but the structure of these files is undocumented
- **No foreign key documentation** — entities like GuarantorEntity and PatientCareTeamEntity have `pid` fields that appear to be foreign keys, but relationships are not formally documented
- **Static snapshot** — generated once (2023-10-25), no version history or changelog

**Could a developer build an import?** Partially. The entity structure and field types are clear. A developer could parse the CBOR and reconstruct the entity graph. However, understanding ~77% of fields would require guessing from names, and coded values (diagnoses, statuses, types) would require reverse engineering from actual data. The 4 fully-documented entities could be imported with confidence; the other 27 would require significant guesswork.

## 7. Overall Assessment

### Classification

**Partial native export** — The export is a genuine serialization of the vendor's internal Java data model (not a FHIR or C-CDA projection), covering 31 entities across clinical, billing, insurance, and operational domains. However, documentation is thin: only 23% of fields have descriptions, no value sets are documented, no sample data is provided, and the export mechanism itself is undocumented. Coverage gaps exist in care plans and consents.

### Key Findings

1. **Genuinely (b)(10)-oriented**: This is a real native data model export — 31 Java entities with 715 fields exported in CBOR format. It is NOT a repackaged FHIR or C-CDA export. It covers billing (`TransactionsEntity`, `PaymentEntity`), insurance (`InsuranceDataEntity`), case management (`CasesEntity`), messages, tasks, and other data well beyond USCDI.

2. **Broad but poorly documented**: 31 entities spanning most data domains the product stores, but only 164 of 715 fields (22.9%) have descriptions. Only 4 entities are fully documented (PatientEntity, CasesEntity, InsuranceDataEntity, InsuranceDataAuthorizationsEntity). The other 27 entities provide only field names and Java types.

3. **CBOR format is unusual**: CBOR (RFC 8949) is a legitimate binary serialization standard with wide library support, but it is not used by any other EHR vendor for EHI export. It adds a decoding step and makes the export non-human-readable. The vendor provides a link to CBOR libraries but no sample data.

4. **No export workflow documentation**: There are zero instructions for how to request, initiate, or configure an export. The documentation covers only the data structure, not the process.

5. **Strong insurance/case documentation contrasts with weak clinical documentation**: InsuranceDataEntity and CasesEntity are fully documented with clear field descriptions. Most clinical entities (medications, allergies, problems, vitals, orders) have zero field descriptions despite having substantial field counts.

### Bottom Line

AllegianceMD built a genuine (b)(10) export of their native data model — 31 entities covering clinical, billing, and operational data — which is the right approach. However, 77% of fields lack descriptions, no value sets are documented, no sample data is provided, and the export process itself is undocumented. A patient or developer receiving this export would get broad data but would struggle to interpret most of it without significant reverse engineering. The single biggest gap is documentation quality: the data model is there, but the documentation needed to use it is largely missing.
