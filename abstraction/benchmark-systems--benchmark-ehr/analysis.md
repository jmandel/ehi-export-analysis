# EHI Export Analysis: Benchmark Systems

**Product**: Benchmark EHR
**Analysis date**: 2026-02-16
**CHPL IDs**: 15.04.04.1144.AntW.71.01.1.171219 (CHPL ID 9098)

## 1. Product Context

Benchmark EHR (now Benchmark Solutions, a division of Harris Healthcare) is a cloud-based, ONC-certified ambulatory EHR serving independent and small medical practices across 27+ specialties. It is part of an integrated suite with Benchmark PM (Practice Management) and Benchmark RCM (Revenue Cycle Management), though the certification is under "Benchmark EHR."

Key data domains the product stores:
- **Clinical**: Patient charts, progress notes, encounter documentation, problems/diagnoses, medications/e-prescribing, lab results, allergies, immunizations, vitals, procedures, surgical history, family/social history, radiology results, consults, referrals, care plans (via CCD), clinical quality measures
- **Administrative**: Patient demographics, insurance information, appointments/scheduling, patient messages (portal), patient alerts/notes, document scanning/attachments, letters/correspondence
- **Billing/Financial**: Superbills, CMS-1500 claims, charge entry, payment posting, ledger, patient statements, advance payments, collections, workers' comp cases
- **Specialty**: 40+ specialty-specific templates; product supports cardiology, dermatology, OB/GYN, oncology, orthopedics, and many others

The tight integration between EHR and PM modules means patient records span clinical and billing domains. The (b)(10) export should ideally cover both.

## 3. Export Mechanics

- **Format**: ZIP file containing XLS (Excel) files for structured data, TXT files for text data, PDF files for documents/attachments, and HTML/XML files for CCD documents
- **Mechanism**:
  - **Single patient**: Self-service via EHR UI. User must have `CuresEHIExport` role. Users select a patient, choose data element types via checkboxes, and trigger an async export. The ZIP file is available under Settings → Configuration → Download Files → "Cures EHI Export" category.
  - **Patient population (bulk)**: Not self-service. Requires contacting the "Bizmatics Data Migration Team" at support@bizmaticsinc.com. Described as resource-intensive and vendor-managed.
- **Single-patient vs bulk**: Both supported, but bulk requires vendor assistance — a potential information-blocking concern under (b)(10)(ii).
- **Access constraints**: Export role `CuresEHIExport` must be assigned; no export password required for this role. Population export depends on vendor schedule.
- **Fees**: Not mentioned in the documentation.

## 5. Coverage Assessment

### 5a. What the vendor covers (bottom-up)

The export is organized around the vendor's internal database model with 47 named entity types. Coverage is notably deep in two areas:

**Billing/financial data** (339 fields across 5 entities): This is the strongest signal that the export is purpose-built. Billing Claims alone has 185 fields covering CMS-1500 claim details, EDI submission tracking, ERA (Electronic Remittance Advice) amounts, assignment/benefits fields, and claims workflow state. Billing Charges adds 124 fields of line-level detail including primary/secondary/tertiary payer amounts, write-offs, and modifier codes. Patient Advance covers advance payments with 30 fields.

**Demographics** (131 fields): Unusually thorough — includes race, ethnicity, language, sexual orientation, gender identity, 5 PCP slots with full NPI/taxonomy, employer data, guarantor references, and multiple emergency contact fields.

**Clinical data** (351 fields across 21 entities): Covers the standard ambulatory clinical record — encounters/progress notes, diagnoses, medications, labs (both order-level and discrete results), vitals, allergies, immunizations, procedures, consults, radiology, prescriptions. All with appropriate standard code systems (ICD-10, SNOMED, LOINC, CVX, RxNorm, NDC).

**Documents/correspondence**: Legal documents, other documents, encounter attachments, old progress notes, and letters are exported as PDF files.

**Thinnest areas**: Some entities have very few fields — Surgery (6), Messages (5), Procedure Notes (3), Health Maintenance (7). Patient Notes, Patient Alert, and Past Appointments have descriptions but no explicit field lists. All Vitals is listed separately from Vitals but with no independent field list (same fields as Vitals #24 but across all encounters).

## 6. Documentation Quality

**Strengths:**
- **Genuine (b)(10) documentation**: A dedicated 28-page self-attestation document, not a pointer to FHIR or C-CDA specs
- **Field-level granularity**: 1,146 named database column fields — this is the vendor's actual internal schema exposed
- **Scope breadth**: 47 entity types covering clinical, billing, documents, and administrative data
- **Practical export instructions**: Clear description of export role, UI workflow, and download location
- **Honest about limitations**: Documents what's excluded (inactive records, void claims, UB04, deleted encounters)

**Weaknesses:**
- **No field descriptions**: All 1,146 fields are database column names only (e.g., `PT_BOOL_SELFPAY`, `BLH_CELL19_LOCALUSE`). While many are self-explanatory, some are opaque without context.
- **No data types**: No column types (string, integer, date, boolean, etc.) despite many `BOOL_*` and `_DATE` fields
- **No value sets**: Fields like `PT_MARITAL_STATUS`, `BLH_CLAIM_STATUS`, `TEI_STATUS_NAME` use coded values that are not defined
- **No relationship documentation**: No foreign key or ERD. Shared ID fields (e.g., `PT_ID` appearing across entities) imply relationships but they are not documented.
- **No sample data**: No example export files or sample records
- **No machine-readable schema**: The data dictionary is embedded in a PDF — no JSON schema, XSD, or other parseable format
- **Original URL returns 403**: The live benchmarksystems.com URL is inaccessible; the document was only retrievable via the Wayback Machine (Feb 2024 snapshot)
- **11 entities with no field lists**: Entities like Patient Notes, Patient Alert, Past Appointments, Billing Ledger, and All Vitals have descriptions but no explicit field enumeration

**Developer usability**: A developer could identify what data is in the export from the column names (most follow a `PREFIX_DESCRIPTIVE_NAME` convention), but could not build a robust import without additional metadata about types, constraints, value sets, and relationships. The documentation is functional but not self-sufficient.

## 7. Overall Assessment

### Classification

**Axis 1 — Coverage breadth: Comprehensive**

This export demonstrably covers the breadth of data domains that Benchmark EHR stores. The 47 entity types span clinical documentation, diagnoses, medications, labs, imaging, vitals, allergies, immunizations, procedures, orders, consults, encounters/progress notes, patient demographics, insurance, documents/attachments, correspondence, scheduling, case management, and — critically — billing claims (185 fields), charges (124 fields), and payments. For an ambulatory EHR/PM product, this covers essentially all patient-facing data domains.

The billing coverage is the strongest signal: 339 fields across 5 billing entities, with Billing Claims alone at 185 fields covering CMS-1500 details, EDI tracking, and ERA (remittance advice) data. This goes far beyond what any USCDI or clinical exchange export would include.

The only notable gaps are structural: specialty template data is exported as rendered PDFs rather than discrete structured fields, and care plans have no dedicated entity. These are minor relative to the overall breadth.

**Axis 2 — Export approach: Purpose-built EHI export**

This is clearly a purpose-built export for (b)(10). The evidence:

1. **Native database model**: Field names like `PT_FNAME`, `BLH_CLAIM_STATUS`, `LOD_TEST_LOINC` are internal database column names — this is the vendor's actual schema, not a projection into FHIR or C-CDA.
2. **Billing data**: 339 fields of billing/financial data that would never appear in a (g)(10) FHIR API or C-CDA exchange.
3. **Workers' comp / case management**: 41 fields for patient cases including injury details, adjuster/attorney references, and approved amounts — operational data not in any clinical exchange standard.
4. **Reference entities**: Insurance Master, Medics, Referring Doctors, Adjusters, Attorneys, Employers — reference data that supports the patient record but has no clinical exchange equivalent.
5. **No reference to FHIR, US Core, or USCDI**: The document is entirely about the vendor's proprietary export format with no attempt to map to or reference any clinical exchange standard (except noting which code systems fields use).
6. **Dedicated export role and UI**: `CuresEHIExport` role with a purpose-built export dialog, not a repurposed clinical document exchange feature.

### Key Findings

1. **Genuinely comprehensive (b)(10) export**: 47 entities with 1,146 database column fields spanning clinical, billing, administrative, and document data. This is one of the more thorough ambulatory EHR (b)(10) exports — particularly the 339 billing fields.

2. **Documentation lacks metadata**: Despite having 1,146 named fields, none have descriptions, data types, or value set definitions. The column naming convention (`PREFIX_DESCRIPTIVE_NAME`) provides reasonable self-documentation, but formal metadata is absent.

3. **Billing coverage is conditional**: The 5 billing entities (Billing Claims, Billing Charges, Billing Ledger, Patient Advance, Statements) only appear "when Billing is turned on for the clinic." Practices without billing enabled would miss 339 fields of financial data.

4. **Population export requires vendor contact**: Bulk export is not self-service — it requires contacting the "Bizmatics Data Migration Team." This creates a dependency on vendor responsiveness and may raise information blocking concerns under (b)(10)(ii).

5. **Primary documentation source is inaccessible**: The registered CHPL URL returns HTTP 403; the PDF was only retrievable from the Wayback Machine. The vendor (now under Harris Healthcare) has not maintained public access to this documentation.

### Bottom Line

Benchmark EHR has built a genuine (b)(10) export that exposes the vendor's internal database schema across 47 entity types covering clinical, billing, administrative, and document data. A patient or provider would get a substantively complete copy of their ambulatory record, including detailed claims and charge data (185 and 124 fields respectively). The biggest weakness is documentation quality — 1,146 fields with no descriptions, types, or value sets — and the inaccessibility of the documentation URL itself.
