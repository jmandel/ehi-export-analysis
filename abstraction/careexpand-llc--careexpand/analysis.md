# EHI Export Analysis: Careexpand LLC

**Product**: Careexpand v2024.11.0
**Analysis date**: 2026-02-15
**CHPL IDs**: 11625 (15.04.04.3226.Care.24.00.1.250422)

## 1. Product Context

Careexpand is a cloud-based, all-in-one healthcare platform combining EHR, telemedicine, remote patient monitoring (RPM), care coordination, and practice management. Built by a small startup (1–10 employees, founded 2016, certified April 2025), it targets individual doctors and small clinics with three pricing tiers:

- **Telemedicine Plan** ($49/mo): video/phone consultations, scheduling
- **Continuity of Care Plan** ($149/mo): adds care coordination, referral management
- **Full Practice Management Plan** ($249/mo): adds EHR, e-prescribing, lab orders, billing, CQMs

Based on its certified criteria and marketed features, Careexpand stores:

- **Clinical data**: demographics, problem lists, medications, allergies, vitals, lab results, procedures, encounters, clinical notes with AI-assisted coding, implantable device lists, care plans
- **E-prescribing data**: prescriptions, protocols for chronic conditions
- **Telemedicine data**: video/phone consultation records, virtual visit data
- **RPM data**: device readings for diabetes, hypertension, heart disease monitoring
- **Care coordination**: referrals, follow-up protocols, transitions of care
- **Administrative**: scheduling, billing (at $249/mo tier), reporting, CQMs
- **Patient engagement**: portal communications, intake forms, messages

The product is certified for (b)(10) EHI Export, (b)(1) Transitions of Care, (b)(11) Care Plans, (a)(1) CPOE, (a)(5) Demographics, (a)(14) Implantable Devices, (g)(10) FHIR API, and (h)(1) Direct Messaging, among other criteria.

## 3. Export Mechanics

- **Format**: C-CDA 2.1 XML (Consolidated Clinical Document Architecture)
- **Mechanism**: Authenticated API endpoint — `POST /patient/:idPatient/getPatientCCDAData` with JWT Bearer Token
- **Single-patient only**: The documented endpoint takes a single patient ID parameter. No bulk export endpoint is documented.
- **Access constraints**: Requires JWT authentication via JwtAuthGuard. No documentation on how end users (patients or providers) trigger the export through the UI — only an API specification is provided.
- **Output**: A JSON response containing a `patientData` object with `demographics`, `clinicalData`, and `monitors` sub-objects, plus a link to download a `.xml` C-CDA file. The relationship between the JSON response and the C-CDA XML file is ambiguous — the documentation doesn't clarify whether the JSON is the primary output or just a wrapper around the XML download link.
- **Fees**: Not mentioned in the documentation.

## 4. Export Content: What's In It

### Data Dictionary

The entire data dictionary consists of **17 fields** presented as a PNG image (not as structured text or an HTML table). All 17 fields have brief descriptions, data types, and required/optional designations.

**Field type breakdown**:
- 9 String fields (demographics + smoking status)
- 7 Array (Structured) fields (clinical data categories)
- 1 Date field (dob)

**Required vs Optional**:
- 7 required: patient_name, dob, gender, problem_list, medications, allergies, encounters

## 5. Coverage Assessment

### 5a. What the vendor covers (bottom-up)

The export documentation describes a **standard C-CDA clinical summary** — the same clinical data classes available through a Transitions of Care (b)(1) export or FHIR (g)(10) API. The 17 fields map directly to standard C-CDA sections:

- **Demographics** (9 fields): name, DOB, gender, race, ethnicity, language, address, phone, emergency contact — these are standard C-CDA header elements
- **Social history** (1 field): smoking status — a standard C-CDA section
- **Clinical data** (7 arrays): problems, medications, allergies, labs, procedures, encounters, vitals — all standard C-CDA sections

This is exactly the USCDI v1 core data set. There is nothing beyond what a basic C-CDA Continuity of Care Document would contain. No vendor-specific extensions, no additional data domains, no custom fields.

## 6. Documentation Quality

The documentation quality is **very poor**:

- **Scope**: The entire EHI export documentation is a single wiki page, 4 PDF pages. This documents what should be a comprehensive export of all patient data in the system.
- **Data dictionary is an image**: The sole data dictionary is a PNG screenshot embedded in the wiki page — not searchable, not machine-readable, not parseable. No HTML table, no CSV, no JSON schema.
- **No sub-field documentation**: The 7 "Array (Structured)" clinical fields have no internal structure documented. A developer cannot know what fields a `medications` entry contains without calling the API and reverse-engineering the output.
- **No sample data**: No example C-CDA XML output is provided. No sample request/response.
- **No schema files**: No XSD, Schematron, or profile definitions.
- **No value sets**: No code systems referenced (no ICD, SNOMED, RxNorm, LOINC, CPT).
- **No relationships**: No entity relationships documented.
- **Placeholder JSON**: The response structure example uses comments (`// Clinical information`) instead of actual field definitions.
- **Undefined request type**: `PatientCCDADTO` is referenced as the request body type but never defined.
- **Ambiguous output**: It's unclear whether the JSON response contains the clinical data inline or just provides a download link for the C-CDA XML file.

A developer could not build an import from this documentation alone. They would need to call the API, receive actual output, and reverse-engineer the data structure.

## 7. Overall Assessment

### Classification

**Standard-based projection** — The export is a C-CDA 2.1 document, which is a standard clinical summary format. It covers the same data classes as a Transitions of Care (b)(1) export or FHIR US Core (g)(10) API response. This is not a native database export — it is a projection of a small subset of Careexpand's data into a clinical document standard. The C-CDA format is structurally incapable of representing billing data, RPM readings, telemedicine session metadata, patient portal messages, or most of the other data types Careexpand stores.

### Key Findings

1. **The (b)(10) export is a repackaged C-CDA clinical summary.** The 17 documented fields map exactly to standard C-CDA sections (demographics, problems, meds, allergies, labs, procedures, encounters, vitals, smoking status). This is the same data available through (b)(1) Transitions of Care — calling it "(b)(10) EHI Export" does not make it a comprehensive export of all electronic health information.

2. **At least 10 applicable EHI domains are missing.** The product stores clinical notes, care plans, orders/referrals, billing records, patient communications, RPM device data, telemedicine records, implantable device data, insurance information, and detailed e-prescribing data — none of which appear in the export documentation.

3. **The data dictionary is a 17-field PNG image.** The sole field-level documentation is a screenshot embedded in a wiki page. It documents top-level categories, not actual fields. The 7 "Array (Structured)" clinical entries have zero internal documentation.

4. **No sample data, no schemas, no machine-readable artifacts.** The documentation provides no example output, no schema files, no value set references, and no worked examples. A developer cannot implement an import from these docs.

5. **Single-patient API only, no bulk export documented.** The export endpoint takes a single patient ID. There is no documented mechanism for bulk or organization-wide export as contemplated by (b)(10).

### Bottom Line

Careexpand's (b)(10) export is a standard C-CDA clinical summary repackaged as an EHI export — a textbook case of the most common compliance failure mode. A patient or provider would receive basic demographics and a clinical summary (problems, meds, allergies, labs, vitals) but would miss the majority of their data: clinical notes, care plans, billing records, RPM readings, telemedicine session data, portal messages, referrals, and e-prescribing details. The single biggest gap is that this is not an export of Careexpand's native data model at all — it is a projection into a standard that can represent perhaps 20% of the data the product stores.
