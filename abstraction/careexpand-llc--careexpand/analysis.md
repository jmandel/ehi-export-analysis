# EHI Export Analysis: Careexpand LLC

**Product**: Careexpand v2024.11.0
**Analysis date**: 2026-02-16
**CHPL IDs**: 11625 (15.04.04.3226.Care.24.00.1.250422)

## 1. Product Context

Careexpand is a cloud-based, all-in-one healthcare platform combining EHR, telemedicine, remote patient monitoring (RPM), care coordination, and practice management. The company is a small startup (~1-10 employees) founded in 2016 and recently certified (April 2025). It targets individual doctors, small clinics, and multi-provider groups, with a focus on ambulatory/outpatient care, primary care, and chronic disease management.

The product is offered in three tiers:
- **Telemedicine Plan** ($49/mo): Video/phone consultations, basic scheduling
- **Continuity of Care Plan** ($149/mo): Care coordination, referral management, follow-up protocols
- **Full Practice Management Plan** ($249/mo): EHR, e-prescribing, lab orders, billing, reporting, CQMs

Based on certified criteria and product documentation, Careexpand stores:
- **Clinical data**: Demographics, problem lists, medications, allergies, lab results, vitals, procedures, encounters, care plans, clinical notes, implantable device lists, prescriptions
- **Telemedicine data**: Video/phone consultation records, patient portal communications, direct messaging
- **RPM data**: Remote monitoring device readings (diabetes, hypertension, heart disease)
- **Administrative data**: Scheduling, billing, referral tracking
- **E-prescribing data**: AI-assisted prescriptions, pharmacy data

This product has certified criteria for CPOE (a)(1), demographics (a)(5), implantable devices (a)(14), transitions of care (b)(1), EHI export (b)(10), care plans (b)(11), and FHIR API (g)(10), among others.

## 3. Export Mechanics

- **Format**: C-CDA 2.1 XML
- **Mechanism**: API call — `POST /patient/:idPatient/getPatientCCDAData`
- **Authentication**: JWT Bearer Token with JwtAuthGuard
- **Request body**: `PatientCCDADTO` (referenced but never defined in the documentation)
- **Response**: JSON envelope containing `patientData` with `demographics`, `clinicalData`, and `monitors` sub-objects, plus a link to download a `.xml` C-CDA file
- **Single-patient only**: The API takes a single `idPatient` parameter. No bulk export mechanism is documented.
- **Access constraints**: Requires valid JWT authentication. No mention of patient-facing self-service export. No fees mentioned.
- **No UI mechanism described**: The documentation describes only an API endpoint, not a user-facing export button or workflow.

## 5. Coverage Assessment

### 5a. What the vendor covers (bottom-up)

The vendor describes a single C-CDA export covering standard clinical summary data. Using the vendor's own terms:

**Demographics** (10 fields): patient_name, dob, gender, race, ethnicity, language, address, phone, emergency_contact, smoking_status. These are basic USCDI demographic elements.

**Clinical data** (7 "Array (Structured)" fields): problem_list, medications, allergies, lab_results, procedures, encounters, vital_signs. These map directly to standard C-CDA sections. No detail is provided about what sub-fields each array contains, what coding systems are used, or how structured the data actually is.

**Monitors** (hinted at): The JSON response structure includes a `monitors` array, but it is not documented in the data dictionary and has only a placeholder comment. This may contain RPM data, but there is no way to know from the documentation.

This is precisely the data set you would expect from a **transitions of care (b)(1)** C-CDA document or a **FHIR US Core (g)(10)** response. It covers the USCDI core clinical data classes and nothing more.

## 6. Documentation Quality

**Very poor.** This is minimal compliance-checkbox documentation:

- **Scope**: The entire EHI export documentation is a single wiki page (~4 printed PDF pages). There is no separate data dictionary document, no schema, no implementation guide.
- **Data dictionary is an image**: The 17-field data dictionary is a PNG screenshot embedded in the page, not structured text. It cannot be queried, searched, or machine-parsed.
- **No sub-field documentation**: The 7 "Array (Structured)" fields — which represent all clinical data — have zero documentation of their internal structure. What fields does a medication entry contain? What coding systems are used for problems? Unknown.
- **Response structure is placeholder**: The JSON example uses comments (`// Clinical information`, `// Patient monitoring data`) instead of actual field definitions.
- **PatientCCDADTO is undefined**: The request body type is referenced but never documented.
- **No sample data**: No example C-CDA output, no sample XML, no sample JSON response.
- **No schema files**: No XSD, no Schematron, no FHIR profile, no JSON schema.
- **No value sets**: No coded fields are documented with value sets or code systems. Gender is "String (M/F/Other)" with no code system reference.
- **No relationships**: No entity relationships, no foreign keys, no relational model.
- **Ambiguous output**: The documentation describes both a JSON response structure and a C-CDA XML download, but doesn't clearly explain how they relate — does the JSON contain the C-CDA inline? Is it a wrapper? Is the XML a separate download?

**Could a developer build an import from this documentation alone?** No. A developer would need to call the API, receive an actual C-CDA file, and reverse-engineer the output. The documentation provides no useful detail about the structure of the clinical data sections.

## 7. Overall Assessment

### Classification

**Standard-based projection** — The export is a C-CDA 2.1 document, which is a standard clinical summary format. It covers the same data classes as a transitions-of-care document or FHIR US Core response. It is not a native data model export. The vendor is using their existing C-CDA capability (likely the same one certified under (b)(1) Transitions of Care) as their (b)(10) EHI export.

### Key Findings

1. **Classic C-CDA repackaging as (b)(10)**: The export is a standard C-CDA clinical summary — the same format used for transitions of care (b)(1). This covers perhaps 20-30% of what the product stores. The 17 documented fields map directly to standard C-CDA sections (demographics, problems, medications, allergies, labs, procedures, encounters, vitals). This is not an "all EHI" export.

2. **Major data domains missing**: Clinical notes, care plans (despite (b)(11) certification), orders/referrals (despite CPOE (a)(1) certification), implantable devices (despite (a)(14) certification), telemedicine records, RPM data, billing data, patient communications, and insurance data are all absent from the documented export. These are core product features.

3. **Data dictionary is an image, not data**: The only data dictionary is a PNG screenshot of 17 fields. It is not machine-readable, not searchable, and cannot be programmatically parsed. This is the minimum possible documentation effort.

4. **7 of 17 fields have no sub-field detail**: The clinical data fields (problem_list, medications, allergies, lab_results, procedures, encounters, vital_signs) are documented only as "Array (Structured)" with a one-sentence description. Their internal structure is completely undocumented.

5. **No sample data or schema**: No example exports, no XML schema, no JSON schema, no worked examples. A developer cannot implement against this documentation without reverse-engineering the actual API output.

### Bottom Line

Careexpand's (b)(10) EHI export is a standard C-CDA clinical summary repackaged as an "all EHI" export — a textbook example of the most common (b)(10) compliance failure mode. A patient or provider requesting their complete electronic health information would receive only basic demographics and standard clinical summary data, missing clinical notes, care plans, telemedicine records, RPM data, billing records, referrals, prescribing details, and patient communications — all of which the product stores. The documentation itself is a single wiki page with a 17-field data dictionary embedded as a PNG image, providing no meaningful guidance for data consumers.
