# EHI Export Analysis: DOX EMR

**Product**: DOX EMR v5.2
**Analysis date**: 2026-02-16
**CHPL IDs**: 10806 (15.02.05.1317.DOXE.01.01.1.220131)

## 1. Product Context

DOX EMR is a cloud-based, specialty-specific EHR and practice management system designed exclusively for podiatry. Founded in 2002 by Dr. Bart Ripperger (a podiatrist in Scottsdale, AZ), it is a very small vendor with a minimal market footprint. The product combines EMR, practice management, and billing into a single integrated platform.

Key data domains the product stores:

- **Patient demographics and insurance** — managed via front office module
- **Podiatry-specific clinical documentation** — pre-built medical database covering "all location, diagnosis, treatment, and plan options for conditions below the knee"; encounter notes, assessments, treatment plans
- **Medications and allergies** — displayed alongside patient histories
- **E-prescribing and orders** — autogenerated from clinical documentation; drug-drug/drug-allergy interaction checking (certified (a)(4))
- **Lab results** — accessible through the patient portal
- **Billing and revenue cycle** — integrated billing with automatic CPT and ICD code extraction from clinical records, invoice creation, payment monitoring, insurance claim management
- **Scheduling** — appointment management with reminders
- **Patient portal** — patient-completed medical histories, access to records and lab results
- **Clinical quality measures** — MIPS/Meaningful Use reporting
- **Research data** — the Starwriter component collects structured clinical data for health economics and outcomes research

The product is certified for (b)(10) EHI export, (g)(10) Standardized API (FHIR via Aidbox), (b)(1) transitions of care, and a full set of clinical documentation criteria.

## 3. Export Mechanics

- **Format**: C-CDA XML
- **Standard**: USCDI v1
- **Mechanism**: The documentation states "authorized users can generate" the export, implying a UI-driven mechanism, but no instructions for how to initiate or receive the export are provided
- **Scope**: Single patient and "patient population" (bulk) export are both mentioned
- **Access constraints**: No information provided about access constraints, fees, or turnaround time
- **Separate from FHIR API**: The (b)(10) export (C-CDA) is distinct from their (g)(10) FHIR API (built on Health Samurai Aidbox), which supports US Core resources and Bulk Data API

## 7. Overall Assessment

### Classification

**Minimal/stub** — The documentation is too thin to assess export content. What is documented (C-CDA XML, USCDI v1) structurally limits the export to a clinical summary that cannot cover the full designated record set. The b(10) export appears to be a repackaging of the same clinical data available through C-CDA/USCDI v1 — likely overlapping substantially with what the vendor's (g)(10) FHIR API already provides.

### Key Findings

1. **The entire (b)(10) documentation is 62 words with zero vendor-specific content.** The page contains 3 sentences and a link to the generic HL7 C-CDA standard. No data dictionary, schema, sample data, or export instructions exist. (Source: `downloads/b10doc-page.html`, verified via live fetch 2026-02-16)

2. **The export format (C-CDA XML) is structurally incapable of representing the full designated record set.** C-CDA is a clinical document standard with no sections for billing, insurance, payments, scheduling, or specialty-specific structured data — all of which DOX EMR stores. (Source: vendor's stated format per `b10doc-page.html`)

3. **The vendor's most distinctive data — its podiatry-specific clinical database — is not documented as part of the export.** DOX EMR's core differentiator is a pre-built database covering "all location, diagnosis, treatment, and plan options for conditions below the knee." Whether and how this structured specialty data maps into C-CDA generic sections is completely undocumented. (Source: `product-research.md` establishing product capabilities; `b10doc-page.html` showing absence of mapping documentation)

4. **Integrated billing data is entirely excluded by format choice.** The product extracts CPT and ICD codes from clinical records, creates invoices, manages insurance claims, and tracks payments. None of this has a home in C-CDA. (Source: product capabilities per `product-research.md`; C-CDA format limitations)

5. **The (b)(10) export likely provides no additional data beyond the (g)(10) FHIR API.** Both cover USCDI v1 data classes. The b(10) page delivers it as C-CDA XML; the g(10) API delivers it as FHIR R4. The substantive coverage appears identical, defeating the purpose of having a separate (b)(10) "all EHI" export. (Source: comparison of `b10doc-page.html` with FHIR API page at `doxemr.com/dox-hs-aidbox-apis` per `ehi-export-report.md`)

### Bottom Line

DOX EMR's (b)(10) documentation is a 62-word compliance placeholder that points to the generic C-CDA standard. A patient or provider would receive, at best, a clinical summary in C-CDA format — the same data available through the vendor's FHIR API — while billing records, insurance data, payments, and the product's distinctive podiatry-specific structured clinical database would be absent. This is a textbook example of a vendor repackaging their existing clinical document export as a "(b)(10) EHI export" without addressing the regulatory requirement to export **all** electronic health information the system stores.
