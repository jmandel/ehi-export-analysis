# EHI Export Analysis: DOX EMR

**Product**: DOX EMR v5.2
**Analysis date**: 2026-02-15
**CHPL IDs**: 15.02.05.1317.DOXE.01.01.1.220131 (CHPL #10806)

## 1. Product Context

DOX EMR is a cloud-based, specialty-specific electronic medical records and practice management system designed exclusively for **podiatry practices**. Developed by Dr. Bart Ripperger, DPM, a practicing foot and ankle surgeon in Arizona, the product is marketed as a fully integrated EMR/PM platform with a pre-built podiatry database covering "all location, diagnosis, treatment, and plan options for conditions below the knee."

Key modules and data domains relevant to EHI export completeness:

- **Clinical documentation**: Podiatry-specific assessments, diagnoses, treatment plans, clinical notes with structured podiatric data
- **E-prescribing / Orders**: Autogenerated orders, prescriptions, referrals, lab orders, imaging requests
- **Billing & Revenue Cycle**: Integrated billing with automatic CPT/ICD code extraction, claims, invoices, payments, insurance management
- **Front Office**: Scheduling, patient demographics, insurance information
- **Patient Portal**: Patient-completed medical histories, lab results access, appointment viewing
- **Clinical Quality Measures**: MIPS/Meaningful Use reporting
- **Interoperability**: FHIR API (via Health Samurai Aidbox), Direct messaging, C-CDA transitions of care
- **Research data**: Starwriter component for structured clinical data collection (HEOR/RWE research)

This is a full-featured clinical + billing system. A complete EHI export should cover all of these domains.

## 7. Overall Assessment

### Classification

**Minimal/stub**

The documentation is three sentences stating the export is C-CDA XML with USCDI v1 compliance. There is no data dictionary, no schema, no sample data, no export instructions, and no downloadable artifacts of any kind. The export format (C-CDA) is structurally incapable of representing the product's full data model — particularly billing data, podiatry-specific structured clinical data, orders, insurance, and patient portal data. This is a textbook case of C-CDA/FHIR repackaging being called "(b)(10)," combined with documentation so thin that even the C-CDA content cannot be independently assessed.

### Key Findings

1. **The entire (b)(10) documentation is 3 sentences and 1 link.** The page at doxemr.com/b10doc contains a single paragraph stating the export uses "CCDA xml format that comply with USCDI v1 requirements standards" and links to the generic HL7 C-CDA standard. No vendor-specific documentation exists. (Source: `b10doc-page.html`, verified live 2026-02-15)

2. **C-CDA is structurally incapable of a complete EHI export for this product.** DOX EMR is an integrated EMR + practice management system with billing, insurance management, scheduling, and specialty-specific podiatry data. C-CDA is a clinical document standard with no sections for billing, claims, payments, insurance, orders lifecycle, or specialty-specific structured data. Using C-CDA as the sole export format guarantees significant data domains are excluded.

3. **The product's core differentiator — structured podiatry data — is absent.** DOX EMR's entire value proposition is its pre-built podiatry database covering "all conditions below the knee." This specialty-specific structured data model cannot be represented in standard C-CDA sections. The export documentation makes no mention of how (or whether) this data is exported.

4. **No downloadable artifacts exist.** No data dictionary, no schema, no sample data, no PDF documentation, no export instructions. Zero downloadable files on the (b)(10) documentation page. (Verified by HTML parsing: 0 downloadable file links found.)

5. **The (b)(10) export appears to duplicate the (g)(10) API coverage.** USCDI v1 compliance for C-CDA covers essentially the same data classes as the US Core FHIR profiles used in their (g)(10) Standardized API (built on Health Samurai Aidbox). The (b)(10) export adds no visible value beyond what the FHIR API already provides.

### Bottom Line

DOX EMR's (b)(10) EHI export is a compliance placeholder, not a genuine data export capability. The three-sentence documentation points to a C-CDA/USCDI v1 clinical summary that structurally cannot include the product's billing data, podiatry-specific clinical database, insurance information, orders, or patient portal data. A patient or provider requesting their complete record would receive at most a clinical summary — missing the billing, specialty, and administrative data that DOX EMR stores about them.
