**Product**: DOX EMR v5.2
**Analysis date**: 2026-02-16
**CHPL IDs**: 10806 (15.02.05.1317.DOXE.01.01.1.220131)

## 1. Product Context

DOX EMR is a cloud-based, podiatry-specific EHR and practice management system developed by a small company in Scottsdale, Arizona, founded by podiatrist Dr. Bart Ripperger. The product is an integrated platform combining EMR, practice management, and billing — not a modular system. Key capabilities relevant to export completeness:

- **Clinical documentation**: Pre-built podiatry-specific medical database covering "all location, diagnosis, treatment, and plan options for conditions below the knee," with structured assessments, diagnoses, and treatment plans.
- **E-prescribing and orders**: Autogenerated orders and prescriptions from clinical documentation, drug-drug/drug-allergy interaction checking (certified for (a)(4)).
- **Billing and revenue cycle**: Integrated billing with automatic CPT/ICD code extraction, invoice creation, payment monitoring, insurance claim management, and electronic claims submission.
- **Patient portal**: Patients can complete medical histories online, view appointments, treatment plans, and lab results.
- **Scheduling**: Appointment scheduling with reminders and overbooking prevention.
- **Interoperability**: FHIR API via Health Samurai Aidbox (certified for (g)(10)), Direct messaging (h)(1), transitions of care (b)(1).
- **Clinical quality measures**: MIPS attestation and CQM reporting (certified for (c)(1)–(c)(3)).
- **Research data collection**: The Starwriter component collects structured clinical data for health economics and outcomes research.

This is a small but full-featured ambulatory EHR. A genuine (b)(10) export should cover clinical data, billing records, specialty podiatric assessments, orders, prescriptions, and insurance information at minimum.

## 7. Overall Assessment

### Classification

**Axis 1 — Coverage breadth: Minimal/stub/unclear**

The vendor provides zero documentation of what data is actually in the export. The only statement is that it uses C-CDA XML with USCDI v1 compliance. Even taking this at face value, C-CDA/USCDI v1 structurally cannot represent DOX EMR's billing data, insurance/claims records, podiatry-specific structured clinical database, or patient portal data. The documentation is too thin to assess actual coverage, and the stated format (C-CDA USCDI v1) inherently limits the export to clinical summary data — a fraction of what this integrated EMR/PM system stores.

**Axis 2 — Export approach: Repackaged existing export**

The export is explicitly a C-CDA document compliant with USCDI v1 — the same clinical summary format and data scope used for transitions of care under (b)(1) and clinical data exchange. The vendor's own (g)(10) FHIR API (documented on a separate page) covers the same USCDI data classes via US Core profiles. The (b)(10) export is functionally a C-CDA rendering of the same clinical data available through the FHIR API, not a purpose-built EHI export. There is no evidence of any effort to export data beyond what C-CDA/USCDI v1 supports — no billing tables, no specialty-specific data structures, no custom extensions. The vendor explicitly states "USCDI v1 requirements standards" as the scope, which is the clinical exchange floor, not the designated record set.

### Key Findings

1. **The entire (b)(10) documentation is 3 sentences with zero vendor-specific content.** The page at doxemr.com/b10doc contains a heading, a paragraph stating the export uses C-CDA XML with USCDI v1, and a link to the generic HL7 C-CDA standard. No data dictionary, schema, sample data, or export instructions exist. (`downloads/b10doc-page-screenshot.png`, `downloads/b10doc-page.html`)

2. **The export is explicitly scoped to USCDI v1 / C-CDA — the clinical exchange floor, not "all EHI."** By the vendor's own description, the export complies with "USCDI v1 requirements standards," which covers ~15 clinical data classes. This is the same scope as their (g)(10) FHIR API and (b)(1) transitions of care, not a purpose-built EHI export.

3. **Billing, insurance, and claims data — core product capabilities — are structurally excluded.** DOX EMR has integrated billing with automatic CPT/ICD code extraction, claims management, invoice creation, and payment monitoring (`product-research.md`). C-CDA has no sections for billing, claims, or insurance records. These are part of the designated record set and are missing.

4. **The product's core differentiator — podiatry-specific structured clinical data — is likely not captured.** DOX EMR's unique value is its pre-built podiatry database covering "all location, diagnosis, treatment, and plan options for conditions below the knee." This specialty-specific structured data almost certainly exceeds what maps to standard C-CDA problem and procedure sections, but no vendor documentation addresses how (or whether) it is exported.

5. **No downloadable artifacts of any kind exist.** The documentation page has zero PDFs, ZIPs, CSVs, schemas, sample files, or any other machine-readable content. The only external link is to the HL7 C-CDA standard specification.

### Bottom Line

DOX EMR's (b)(10) export is a textbook case of repackaging an existing clinical exchange format (C-CDA) as an EHI export. The documentation is a compliance placeholder — 3 sentences with no vendor-specific content — and the stated C-CDA/USCDI v1 format structurally excludes billing, insurance, and specialty podiatric data that this integrated EMR/PM system stores. A patient requesting their complete health information from DOX EMR would receive a clinical summary, not their full designated record set.
