# EHI Export Analysis: Magilen Enterprises Inc

**Product**: QSmartCare v1.0
**Analysis date**: 2026-02-15
**CHPL ID**: 15.05.05.3098.MAGE.01.00.1.220127 (CHPL #10803)

## 1. Product Context

QSmartCare is a cloud-based specialty wound care EHR built by Magilen Enterprises Inc, the technology arm of Quality Surgical Management (QSM). QSM is a wound care services company that provides bedside wound care in skilled nursing facilities (SNFs) and assisted living facilities across six states. **QSM is the sole user of QSmartCare** — it is not sold to external customers.

Key data domains the product manages:
- **Core wound care charting**: Wound assessments, measurements, photographs (with mobile app edge detection), treatment documentation, healing progress tracking — this is the system's primary purpose
- **Patient demographics**: Including face sheet data imported from host facility EHRs (notably MatrixCare)
- **Clinical data**: Diagnoses, medications (with e-prescribing via NewCrop), allergies, vitals, procedures, care plans, immunizations, lab results
- **Encounters**: Visit documentation for wound care visits at SNFs
- **Wound photography**: Captured via iOS mobile app with auto edge detection
- **Billing/administrative**: The product website mentions serving "billers" and "coders," though the extent of in-system billing functionality is unclear from public materials
- **Patient portal**: Certified for (e)(1), with a login at qsmartcare.com/patient/
- **FHIR API**: 21 FHIR R4 resources via US Core 3.1

The baseline expectation for a complete EHI export: all wound care clinical data (especially wound-specific structured assessments and photographs), demographics, encounters, diagnoses, medications, allergies, vitals, procedures, care plans, and any billing data the system stores.

## 3. Export Mechanics

- **Format**: Two options — PDF (human-readable) and JSON (machine-readable/computable). Both are proprietary formats, not FHIR or C-CDA.
- **Mechanism**: UI-based. Navigate to `Patient > CCDA > Export` in the web application (`qsmartcare.com/app/home.html#/ccda/export`). Click the "EHI Data PDF" or "EHI Data Json" action icon.
- **Single-patient**: Select one patient, click the PDF or JSON icon. File downloads directly.
- **Bulk export**: Select multiple patients via checkboxes, click the PDF or JSON icon. Result downloads as a ZIP file with one file per patient. Screenshot evidence shows the patient list had 3,078 entries, suggesting all patients can be exported.
- **Access constraints**: Requires Author-level permissions within QSmartCare.
- **Fees**: No fees mentioned in documentation. The ONC mandatory disclosures page does not list EHI export fees.

### JSON quality issues

The JSON has significant structural problems that would hinder programmatic consumption:
- **10 string "null" values** (e.g., `"code": "null"`) instead of JSON `null`

## 5. Coverage Assessment

### 5a. What the vendor covers (bottom-up)

The export covers a C-CDA-like cross-section of clinical data organized into 34 labeled sections. The sections map closely to standard C-CDA sections (demographics, problems, medications, allergies, vitals, procedures, immunizations, devices, care plans, encounters). The vendor adds one specialty section — **PATIENT WOUND INFO** — with 8 fields tracking wound location (with anatomical detail: side, sub-location, vertical/horizontal plane), progress, and status.

**Strongest areas**: Demographics (24 fields), implantable devices (12 fields), allergies (9 fields), wound info (8 fields), medications (7 fields).

**Thinnest areas**: Insurance (2 fields — just names, no policy numbers or details), HPI (1 free-text field), anticoagulants (1 field), social/family history (1 field each). Labs section exists but is empty in the sample. Functional and cognitive status sections exist but are empty (LOINC-based placeholders).

**Notable**: The wound data section — the product's core specialty — is surprisingly thin. For a wound care EHR, one would expect wound dimensions (length, width, depth), wound bed characteristics, exudate type/amount, periwound condition, tissue type percentages, wound staging/grading, debridement details, and dressing information. The export shows only location, progress status, and anatomical plane. No wound photographs are included despite the mobile app's photo capture being a key feature.

## 6. Documentation Quality

The documentation is **minimal — a procedural walkthrough with no technical specification**.

**What exists**:
- A Word-to-HTML page (~6 pages of prose) explaining how to navigate to the export and click buttons
- 21 screenshots showing the UI workflow
- Two sample files (PDF and JSON) serving as the de facto format specification

**What's missing**:
- **No data dictionary**: No listing of what fields are included, what they mean, or what data types they use
- **No JSON schema**: No formal specification; the sample file is the only reference
- **No field descriptions**: Field names must be interpreted from context
- **No value sets**: No documentation of valid values for coded fields
- **No relationship documentation**: No foreign keys or entity relationships
- **No completeness statement**: No claim about what's included or excluded
- **No versioning**: Document is dated September 2023 with no change history

**Could a developer build an import?** With difficulty. They would need to reverse-engineer the format from the sample files, discover the PDF/JSON discrepancies, handle the JSON's numbered keys and string "null" values, and accept that many sections have no data to validate against. The lack of schema means any changes to the export format would break consumers silently.

## 7. Overall Assessment

### Classification

**Partial native export** — The export appears to draw from the product's internal data model (not a standard projection), but it has significant coverage gaps, especially for the product's core wound care specialty data, and the documentation is insufficient for practical use.

### Key Findings

1. **The JSON "computable" format is less complete than the PDF** — 12 of 34 sections (36 fields) present in the PDF are absent from the JSON, including insurance, past medical history, labs, blood sugar, pulse oximetry, and functional/cognitive status. This is the single most concrete deficiency: the machine-readable export drops data that the human-readable export includes.

2. **Wound care data — the product's core specialty — is superficially represented.** The PATIENT WOUND INFO section has only 8 fields (location, side, sub-location, planes, status). For a product "built by and for wound care physicians over 30 years," one would expect detailed wound assessments (dimensions, staging, tissue characteristics, exudate, periwound condition) that constitute the heart of the clinical record.

3. **No wound photographs in the export.** The iOS mobile app's wound photography with auto edge detection is a key clinical feature. No images or image references appear in either export format.

4. **No data dictionary, schema, or format specification exists.** The two sample files are the entire technical documentation. A developer cannot build a reliable import without reverse-engineering the format and accepting significant ambiguity.

5. **JSON quality is poor** — 10 string "null" values, 11 numbered key patterns instead of arrays, inconsistent nesting. Despite using FHIR-like `resourceType` labels, the format is entirely proprietary and would confuse consumers expecting FHIR conformance.

### Bottom Line

A patient or provider would receive a recognizable but incomplete copy of their data. The export covers standard clinical domains (demographics, diagnoses, medications, allergies, vitals, procedures) adequately, but critically underrepresents the product's core value — wound care clinical documentation. For a wound care EHR, the absence of detailed wound assessments, wound photographs, and clinical encounter notes means the most important patient data may not be exported. The JSON format's incompleteness relative to the PDF, combined with zero documentation, makes the machine-readable export unreliable for data portability.
