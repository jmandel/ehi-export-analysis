# EHI Export Analysis: Magilen Enterprises Inc

**Product**: QSmartCare v1.0
**Analysis date**: 2026-02-16
**CHPL IDs**: 15.05.05.3098.MAGE.01.00.1.220127 (CHPL #10803)

## 1. Product Context

QSmartCare is a specialty wound care EHR built by and for Quality Surgical Management (QSM), a wound care services company that provides bedside wound care in skilled nursing facilities (SNFs) and assisted living facilities across six states. QSM is the **sole user** of QSmartCare — this is an internal tool, not a commercial EHR product. QSM has treated 171,000+ patients across 605 facilities.

**Core functionality relevant to EHI completeness:**
- **Wound care documentation**: The primary function — wound assessments, measurements, wound photography (via companion iOS app with auto edge detection), treatment tracking, and healing progress. This is the most critical data domain for this product.
- **Clinical charting**: Demographics, encounters, diagnoses, medications, allergies, vitals, procedures, care plans, immunizations, devices.
- **Care transitions**: Bidirectional integration with MatrixCare (major SNF EHR) for patient face sheet data and wound documentation exchange.
- **Billing/coding support**: QSM employs billers and coders, and the product serves administrative staff. However, no explicit billing module is documented publicly — it's unclear whether billing occurs within QSmartCare or a separate system.
- **Patient portal**: Certified for (e)(1) but with low actual usage.
- **E-prescribing**: Via NewCrop integration.
- **FHIR API**: R4 API conforming to US Core 3.1, exposing 21 resource types.

The baseline expectation: the export should cover wound care clinical data (the specialty domain), standard clinical data, and any billing data stored in the system.

## 3. Export Mechanics

- **Format**: PDF (human-readable) and JSON (machine-readable/computable). Both are proprietary formats — the JSON uses FHIR-like terminology but is **not FHIR-conformant**.
- **Mechanism**: UI-driven. Navigate to `Patient > CCDA > Export` in the web application (`qsmartcare.com/app/home.html#/ccda/export`).
- **Single-patient**: Click a patient row, then click either "EHI Data PDF" or "EHI Data Json" icon. File downloads directly.
- **Bulk/multi-patient**: Select multiple patients via checkboxes, click the EHI data icon. Downloads as a ZIP file containing one file per patient (individual PDFs or individual JSONs).
- **Access constraints**: Requires Author-level permissions within the application.
- **Fees**: No fees mentioned in documentation. The ONC costs page lists $0 for certified health IT modules.

## 4. Export Content: What's In It

### Overview

The export is a **flat patient-level dump** — not a database export. Each patient's data is rendered into a single PDF document (32 labeled sections across 7 pages) or a single JSON object (proprietary structure). There is **no data dictionary, no schema, no field-level documentation** from the vendor. The sample files are the only specification.

Based on parsing the sample PDF and JSON (see `analysis/full-entity-inventory.json`):
- **38 data sections/entities** identified across both formats
- **164 unique fields** across all sections
- **0 fields with descriptions** (no data dictionary exists)
- **0 fields with type documentation**
- The **PDF is more complete than the JSON** — 21 sections appear in PDF but not in JSON (insurance, relationships, past medical history, anticoagulants, labs, blood sugar, individual vitals, functional/cognitive status). 4 entities appear only in JSON (goals, assessments, healthConcerns, socialHistory as structured).

### JSON structure notes

The JSON has significant structural issues:
- Uses FHIR-like `resourceType` labels (e.g., `"resourceType": "Patient"`) but is **not FHIR-conformant** — field names are custom (`firstName`, `lastName` vs FHIR's `name[].given`, `name[].family`).
- Everything nests under `object.organization` — patient data, encounters, diagnoses all mixed under the organization key.
- Medications use numbered keys (`codeSystemSnomed0`, `codeSystemSnomed1`) instead of arrays.
- Many coded fields contain `"code": "null"` (string literal "null") or empty strings instead of actual codes.
- Allergy and medication code fields reference "SNOMED" but contain no SNOMED codes.
- No RxNorm codes appear in JSON medications (though they do in the PDF).

### PDF structure notes

The PDF export (source: `Single-Patient-PDF-Download.pdf`, 7 pages, generated by TCPDF 6.2.13) is a formatted report with:
- Practice header on every page (Dr. Steven Magilen's contact info)
- 32 labeled sections with tabular data

- CVX codes for immunizations
- UDI data for implantable devices
- RxNorm codes for medications (column exists, mostly empty in sample)
- LOINC references for functional/cognitive status (empty in sample)

## 5. Coverage Assessment

### 5a. What the vendor covers (bottom-up)

The export covers a **broad but shallow** set of clinical data domains. Using the vendor's own sections:

**Strongest areas** (most fields, most data in sample):
- **Demographics** (24 fields): Comprehensive — name, DOB, gender, race, ethnicity, address, SSN, language, marital status, preferred provider.
- **Allergies** (9 fields): Includes reaction, severity, type, dates, status.
- **Devices** (12 fields): Full UDI data including manufacturer, model, MRI safety, GMDN, FDA codes.
- **Wound data** (8 fields): Location with anatomical detail (side, sub-location, vertical/horizontal plane), progress, status. But see gaps below.

**Moderate areas**:
- **Medications** (7 fields): Name, type, dosage, route, frequency, RxNorm code, status.
- **Diagnoses** (5 fields): ICD-10 coded with dates and status.
- **Procedures** (6 fields): Procedure code, name, dates, outcome, status.
- **Immunizations** (6 fields): CVX coded with dates and status.
- **Vital signs** (19 fields across 8 sub-sections): Individual measurements with dates.

**Thin areas**:
- **Insurance** (2 fields): Only primary and secondary insurance names. No policy numbers, group IDs, coverage dates, or payer details.
- **Clinical notes** (1 field): Only HPI as free text. No progress notes, consultation notes, or other document types.
- **Care plans** (2 fields): Assessment and plan as narrative text only.
- **Encounters** (4 fields): Consult type, chief complaint, DOS, smoking status. Very thin for a wound care practice.
- **Lab results** (4 fields): Section exists but empty in sample. Format shows date, path, name, location.

### Critical observation on wound data

QSmartCare's entire reason for existence is wound care documentation. The product website emphasizes "accelerated charting" with an "intelligent workflow" for wound documentation. The mobile app captures wound photos with auto edge detection. QSM has documented wound care across 605 facilities for 171,000+ patients.

Yet the export contains only 8 wound fields: wound number, DOS, anatomical location (broken into side/sub-location/vertical/horizontal plane), progress, and status. There are **no wound measurements, no staging, no wound bed description, no treatment details, no dressing information, and no wound photographs**. Either the export omits the vast majority of the product's core clinical data, or the sample is unrepresentative — but since no data dictionary exists, there's no way to confirm what the actual export covers beyond the sample.

## 6. Documentation Quality

The export documentation is **extremely thin**:

- **No data dictionary**: No listing of fields, their meanings, data types, or value sets. The vendor provides zero field-level documentation.
- **No schema**: No JSON schema, no format specification. The only way to understand the JSON structure is to reverse-engineer the 8 KB sample file.
- **No export completeness statement**: No claim about what data domains are included, what's excluded, or whether this constitutes "all EHI."
- **No relationships**: No documentation of how entities relate to each other.
- **Procedural only**: The HTML page (61 KB, mostly screenshots) is a step-by-step "how to click the export button" guide. It provides no technical substance.
- **Sample files are the only specification**: A developer would need to reverse-engineer both the PDF layout and JSON structure from the samples, discover the significant discrepancies between them (21 sections in PDF but not JSON), and have no way to resolve ambiguities.
- **No machine-readable artifacts**: No schema files, no API spec, no structured format definition.
- **Stale**: Documentation dated September 2023, no version history.

A developer could not build a reliable import from this documentation alone. They would encounter the JSON's inconsistent patterns (numbered keys, string "null" values), discover missing sections compared to PDF, and have no recourse except contacting the vendor.

## 7. Overall Assessment

### Classification

**Partial native export**

The export uses a proprietary format (not C-CDA, not FHIR) that appears to pull data from the product's internal data model. It covers a broad range of standard clinical domains (demographics, diagnoses, meds, allergies, vitals, procedures, immunizations, devices) plus some wound-specific data. However, documentation is virtually absent, the JSON format is less complete than the PDF, and the specialty wound care data — the product's core value — is strikingly thin.

### Key Findings

1. **The wound care data — the product's raison d'être — is the thinnest part of the export.** Only 8 fields for wound data (location and status), with no measurements, staging, wound bed characteristics, treatment details, or photographs. For a product built over 30 years specifically for wound care documentation, this is a major gap. (Source: `PATIENT WOUND INFO` section, `Single-Patient-PDF-Download.pdf` page 3)

2. **The JSON ("computable") export is significantly less complete than the PDF.** 21 of 32 PDF sections have no JSON equivalent, including insurance, past medical history, labs, blood sugar, and all individual vital sign sections. The "machine-readable" format omits ~65% of the data in the "human-readable" format. (Source: comparison of `sample-ehi-export.json` vs `Single-Patient-PDF-Download.pdf`)

3. **No data dictionary exists.** Zero of 164 identified fields have vendor-provided descriptions, type documentation, or value set specifications. The sample files are the only schema documentation. (Source: `ehi-template.html` contains only procedural screenshots)

4. **Wound photographs are absent.** The product's companion iOS app captures wound photos with auto edge detection — a signature feature for wound care — but no image data or image references appear in either export format. (Source: no image/photo sections in PDF or JSON samples)

5. **Insurance and billing data is minimal to absent.** Insurance section has only primary/secondary insurer names (no policy details). No billing, claims, charges, or payment data appears. Whether billing occurs in QSmartCare or externally cannot be determined from available evidence. (Source: `INSURANCE INFO` section, `Single-Patient-PDF-Download.pdf` page 3)

### Bottom Line

The QSmartCare EHI export covers standard clinical data (demographics, meds, allergies, vitals, diagnoses) at a basic level, but **fails to meaningfully export the product's core specialty data — wound care documentation**. A wound care EHR that exports only wound location and progress status, without measurements, staging, wound bed characteristics, or photographs, is not providing "all electronic health information." The absence of any data dictionary and the significant disparity between the PDF and JSON formats (JSON missing ~65% of PDF sections) further undermine the export's utility. This appears to be a compliance checkbox rather than a genuine effort at data portability.
