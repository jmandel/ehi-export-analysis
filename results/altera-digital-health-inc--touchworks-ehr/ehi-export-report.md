## What Was Found

### Export Format
The EHI export is a **SQL database dump/extract** covering the complete TouchWorks database schema. The documentation describes the structure of the exported data as a relational database with 8 databases and 577 tables containing 7,748 columns.

This is a genuine (b)(10) export — it exports the raw relational database contents, not a FHIR or C-CDA subset. The export covers the full breadth of data stored in TouchWorks EHR.

### Documentation Structure
The documentation is generated by a SQL Server database documentation tool. Each table has its own HTML page with:
- **MS_Description** — a human-readable description of the table's purpose
- **Columns** — name, SQL data type, max length, nullability, default value, description
- **Indexes** — index name, columns, type (clustered/nonclustered)
- **Foreign Keys** — constraint name, local columns, referenced table.columns

## Export Coverage Assessment

### Data Domain Coverage

This is an exceptionally thorough (b)(10) export. The database schema covers essentially **all clinical and billing data** that TouchWorks stores:

**Clearly covered domains:**
- **Patient demographics** — 57 tables including patient communications, cautions, API registrations, portal activity
- **Allergies** — 11 tables (Allergy, Allergen_DE, Allergy_Reactions, etc.)
- **Medications** — 20 tables (Item_Medication, MedicalDevice, Medication_Warning, etc.)
- **Lab results** — 17 tables (Act_Result, Act_Result_Extension, DocumentLabel, etc.)
- **Vitals** — 2 tables (Act_Hdr_Vitals, Act_Vitals)
- **Immunizations** — 8 tables (Immunization, Immunization_Forecast, etc.)
- **Problems/Diagnoses** — 22 tables (Encounter_Diagnosis, ICD10/ICD9 codes, Problem, etc.)
- **Orders** — 21 tables (Order_Activity, Order_Activity_Header, etc.)
- **Notes/Documents** — 30 tables (Document, DocumentInformation, Act_Note, etc.)
- **Encounters** — 24 tables (Encounter, Encounter_CarePlan, Encounter_Case, etc.)
- **Billing/Charges** — 21 tables (Charge, Charge_Diagnosis, Charge_Modifier, Charge_Status, plus AHSCharge database)
- **Insurance** — 2 tables (Insurance_Class_DE, Primary_Insurance)
- **Scheduling** — 8 tables (Appointment, Appointment_Address, Appoint_Segment, etc.)
- **Referrals** — 14 tables
- **Clinical Decision Support** — 21+ CDS tables across Works and WorksCDSAggregatorArchive
- **Document scanning** — 6 tables in IntegratedScan database
- **Reference/Dictionary tables** — 166 lookup tables (DE = dictionary entry) covering coded values for clinical concepts

**Notable coverage strengths:**
- Billing data is well-represented (21+ tables including charges, ABN status, billing areas, charge codes, charge diagnoses, charge modifiers)
- Specialty clinical data is captured through the flexible Act_* table pattern (Act_Allergy, Act_Goal, Act_HMP, Act_MedAdmin, Act_Note, Act_Other, Act_Result, Act_Vitals)
- Extensive dictionary/reference tables (166 _DE tables) document the coded values used throughout the system
- The export includes the full relational model with foreign keys, enabling reconstruction of patient records

**Potential gaps or ambiguities:**
- **Care plans** — Encounter_CarePlan exists, but limited to encounter-level plans
- **Patient-entered data** — Portal activity is tracked (PatientPortalUserActivity) but patient-authored content unclear
- **Revenue cycle depth** — Basic charge tables present, but comprehensive claims/payment data may reside in the separate Ventus product
- **Imaging content** — IntegratedScan has metadata tables, but actual image data storage is unclear (likely blob/file system)

### Export Format & Standards

- **Format**: SQL database export (relational tables)
- **Not a standard format** — it's a proprietary SQL Server database schema, not FHIR, C-CDA, or any standard interchange format
- **Relationships**: Fully documented via foreign keys — a developer could reconstruct patient records by joining tables
- **Value sets**: 166 dictionary/lookup tables (_DE suffix) define coded values inline in the database
- **Appropriate for the data**: Yes — a relational database dump is the most faithful representation of an EHR's internal data model

A third party could reconstruct patient records from this export given the column descriptions, foreign keys, and dictionary tables. The schema is well-structured with consistent naming conventions.

### Documentation Quality

**Strengths:**
- Complete coverage of all 577 tables
- Column-level documentation with data types, lengths, and nullability
- Foreign key relationships enable understanding of the data model
- Table descriptions provide context for each table's purpose
- Generated from the actual database schema, ensuring accuracy
- Multiple versions available, showing active maintenance

**Weaknesses:**
- Only 51.3% of columns have descriptions — many columns are undocumented
- No separate user guide explaining the export process itself (how to request it, what format it arrives in, how to import it)
- No sample data or example export files provided
- No data flow diagrams or entity-relationship diagrams
- Custom data types (e.g., `[dbo].[uniqueid]`) are not explicitly defined
- Dictionary table values (_DE tables) document the structure but not the actual coded values

### Structure & Completeness

- **Granularity**: Field-level documentation with data types, constraints, and partial descriptions
- **Coded fields**: Dictionary tables (_DE) document the structure of value sets but not their content
- **Relationships**: Well-documented via foreign keys
- **Versioning**: Yes — multiple versions available (2022 through 2026), showing evolution
- **No worked examples or sample files**

### Overall Assessment

Altera's TouchWorks EHI export documentation represents a **strong (b)(10) implementation**. Unlike many vendors that simply point to their FHIR/g(10) API, Altera exports the complete SQL database schema — 8 databases, 577 tables, 7,748 columns — covering clinical data, billing, scheduling, reference data, and administrative records. This is clearly a genuine effort to export *all* electronic health information, not just the USCDI subset.

The documentation is generated directly from the database, which ensures accuracy but means it lacks the narrative context a developer would need. A recipient would need significant SQL and healthcare domain expertise to reconstruct meaningful patient records from the raw tables.

The main limitation is that ~49% of columns lack descriptions, making some tables harder to interpret. The documentation would also benefit from an entity-relationship diagram, sample data, and a user-facing guide explaining how to request and use the export.
