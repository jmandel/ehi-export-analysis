## What Was Found

The EHI export documentation is a single HTML page containing a Word-exported document dated September 2023. It is a short procedural guide (equivalent to roughly 6 pages of content) that explains how to use the EHI export feature in QSmartCare. The documentation covers:

### Export Mechanism
The EHI export is accessed via **Patient > CCDA > Export** in the application (URL: `qsmartcare.com/app/home.html#/ccda/export`). The export lives within the C-CDA section of the application, though the EHI export itself is not C-CDA — it produces PDF and JSON files.

### Two Export Modes
1. **Single Patient Export**: Select a patient from the list, then click either "EHI Data PDF" (human-readable) or "EHI Data Json" (machine-readable/computable) icons in the Action column. The file downloads directly.

2. **Multiple Patient Export**: Select multiple patients via checkboxes, then click the "EHI data PDF" or "EHI data Json" icon. The result downloads as a ZIP file containing one file per patient.

### Export Formats
- **PDF format**: A 7-page report generated by TCPDF, organized into labeled sections with tabular data. It contains the practice header (Dr. Steven Magilen's information) on every page.
- **JSON format**: A custom (non-FHIR, non-standard) JSON structure with a single root `object` containing an `organization` key that nests all patient data. Uses FHIR-like `resourceType` labels (e.g., `"resourceType": "Patient"`, `"resourceType": "Medications"`) but the structure is entirely proprietary — not conformant to any FHIR profile or standard.

### Notable Observations About the JSON Structure
- The JSON uses FHIR-like `resourceType` labels but is **not FHIR-conformant**. Field names are camelCase custom fields (e.g., `firstName`, `lastName`, `phoneNumber`) rather than FHIR resource structures.
- Medication entries use numbered keys (`codeSystemSnomed0`, `codeSystemSnomed1`) rather than arrays — an unusual pattern.
- Many coded fields have `"code": "null"` (string "null") or empty strings rather than actual codes.
- The JSON contains **fewer sections than the PDF** — insurance, spouse, patient relationships, past medical history, anticoagulants, labs, blood sugar, functional status, and cognitive status sections appear in the PDF but are absent from the JSON.

### Access Requirements
The documentation states the export requires **Author-level permissions**. The export is accessible within the application at `Patient > CCDA > Export`.

## Export Coverage Assessment

### Data Domain Coverage

**Clearly covered** (present in sample export):
- Patient demographics (comprehensive — name, DOB, gender, race, ethnicity, address, SSN, language, marital status)
- Diagnoses/conditions (ICD-10 coded)
- Medications (with RxNorm codes, dosage, route, frequency)
- Allergies (with severity, reaction, dates)
- Vital signs (comprehensive — BP, HR, temp, weight, height, BMI, O2, respiratory rate, pulse oximetry)
- Procedures/surgical history (coded)
- Immunizations (CVX coded)
- Implantable devices (with full UDI data)
- Encounters (with chief complaint, status history)
- Care plans and treatment plans (narrative)
- Care team members
- Wound data (the core specialty data — location, progress, status with detailed anatomical positioning)
- Social history (smoking status)
- Insurance information (names only — in PDF, not JSON)
- Patient relationships (in PDF, not JSON)

**Potentially missing or thin**:
- **Billing/claims data**: Only insurance *names* appear. No CPT codes, charges, claims, payments, or billing records. The product research notes that QSM employs billers and coders, and the system likely handles billing workflow, but no billing data appears in the export.
- **Wound-specific clinical detail**: While the export includes wound location and status, the sample shows only minimal wound data (1 wound with location, progress, status). For a product built around wound care, one would expect much more detailed wound assessment data — wound dimensions (length, width, depth), wound bed characteristics, exudate type/amount, periwound condition, wound edges, tissue type percentages, wound staging/grading, debridement details, dressing information. These fields are likely in the system but may not appear in the sample because the test patient has minimal data. However, the export format doesn't show *columns* for these fields either, which is concerning.
- **Wound photographs**: The product's mobile app captures wound photos with edge detection — a core clinical feature. No image data or image references appear in the export.
- **Clinical notes beyond HPI**: The export has an HPI section and an Assessment/Plan section, but no progress notes, consultation notes, or other clinical document types. For a wound care practice that documents encounters at 605 facilities, the encounter documentation is likely richer than what's shown.
- **Lab results**: The LAB INFO section exists but is empty in the sample. The format appears to support lab data.
- **Scheduling/appointment data**: Not present, though the mobile app shows schedules.

**Not expected to be in export** (correctly absent):
- Audit logs, system configuration, provider credentialing, quality metrics — these are appropriately excluded.

### Export Format & Standards

The export uses a **proprietary format** — both PDF and a custom JSON structure. This is actually appropriate for a (b)(10) EHI export, as the regulation does not require a standardized format. However:

- The JSON borrows FHIR terminology (`resourceType`, OID identifiers) without being FHIR-conformant, which could create confusion. A consumer expecting FHIR would fail to parse this.
- The JSON structure nests everything under a single `object.organization` path, mixing organizational, location, care team, and patient data into one flat hierarchy. This makes it harder to process programmatically than it needs to be.
- The PDF is more complete than the JSON — several data sections (insurance, relationships, past medical history, labs, blood sugar, functional/cognitive status) appear in the PDF but not the JSON. This means the "computable" format is actually **less complete** than the human-readable format, undermining its utility.
- The JSON has no schema, no data dictionary, and no format specification beyond the sample file itself.
- A third party could extract basic clinical data from either format, but would struggle with the JSON's inconsistent patterns (numbered keys, string "null" values, missing sections).

### Documentation Quality

The documentation is **minimal**. It is a procedural walkthrough — "click here, then click here" — with screenshots. It tells you *how to trigger the export* but provides:

- **No data dictionary**: No listing of what fields are included, what they mean, or what data types they use.
- **No schema specification**: No JSON schema, no format definition. The only way to understand the JSON structure is to read the sample file.
- **No field-level definitions**: No descriptions of fields, value sets, cardinality, or constraints.
- **No explanation of what "EHI" means in context**: No statement of what data domains are included or excluded from the export.
- **No export completeness statement**: No claim about whether this covers all EHI or a subset.
- **No versioning or change history**.
- **Sample data only**: The two sample files (PDF and JSON) are the only way to understand what the export contains. There is no narrative description of the export contents beyond the screenshots.

The documentation appears to be a compliance checkbox — the minimum effort to have *something* at the registered URL. It was generated from a Word document, published as HTML, and has not been updated since September 2023.

A developer attempting to import this data would need to reverse-engineer the format from the sample file. They would discover discrepancies between the PDF and JSON formats and have no way to resolve them without contacting the vendor.

### Structure & Completeness

- **Granularity**: The documentation provides no structured data dictionary. The sample files serve as the de facto schema, but they show only one patient's data, making it impossible to distinguish "this field is always empty" from "this field doesn't exist."
- **Coded fields**: Some ICD-10, CVX, and RxNorm codes appear in the samples. Many SNOMED code fields contain `"null"` strings or empty values. No value set documentation exists.
- **Relationships**: No documentation of how entities relate. The JSON nests everything under a single organization object.
- **Versioning**: No version information. The document is dated September 2023.

### Overall Assessment

This is a small, single-customer wound care EHR (QSmartCare is used only by Quality Surgical Management) that has implemented a basic EHI export. The export covers a reasonable range of clinical data domains — demographics, diagnoses, medications, allergies, vitals, procedures, immunizations, devices, encounters, and care plans — plus wound-specific data (the product's specialty).

However, the export has significant gaps for a wound care product:
1. **Wound photographs** — arguably the most important clinical data for wound care — are absent.
2. **Detailed wound assessment data** (dimensions, staging, tissue characteristics) is not clearly represented.
3. **Billing data** is absent despite the system supporting billing workflows.
4. The **JSON format is less complete than the PDF**, defeating the purpose of a computable export.
5. There is **no data dictionary, schema, or format specification** — just a sample file.

The documentation's brevity and the discrepancies between PDF and JSON formats suggest this was built to satisfy the certification requirement rather than to enable meaningful data portability. Given that QSM is the sole user of this software, the practical impact is limited — but the documentation would not enable a third party to reconstruct patient records from the JSON export alone.
