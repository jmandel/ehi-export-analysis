## What Was Found

### Export Mechanism

Canvas's EHI export is built on top of **FHIR Bulk Data Access** (STU 1.0.1). The export produces **FHIR R4 resources in Newline Delimited JSON (NDJSON)** format.

Two export paths exist:

1. **Single patient export via UI**: Navigate to "Fhir bulk data exports" in admin settings, click "ADD FHIR BULK DATA EXPORT", select an OAuth application, search for a patient, and click "Start Export." This generates downloadable NDJSON files for each resource type. Access is permission-based.

2. **Single patient export via API**: `GET https://fumage-{instance}.canvasmedical.com/Patient/{id}/$export`

3. **Population export**: Contact Canvas support with instance name, username, role, patient group, and purpose. Canvas staff initiates the bulk export on behalf of the customer. Output appears in the same "FHIR Bulk Data Export" admin table.

### Documentation Depth

Each FHIR resource page provides:
- Full field-level attribute documentation (name, type, required/optional, description)
- Value set options for coded fields
- Nested child attribute documentation
- Canvas-specific extensions (e.g., note-id extension, claim queue extension)
- HTTP response codes and error documentation

The FHIR API documentation uses Canvas-specific profiles — these aren't just standard FHIR R4. For example, AllergyIntolerance references US Core STU3.1.1 profile but includes Canvas-specific extensions for note linkage. Claim includes custom queue extensions. Patient includes Canvas-specific extensions for social determinants (housing, education, veteran status, etc.).

## Export Coverage Assessment

### Data Domain Coverage

Canvas's internal data model (as documented in the SDK) has **51 data model pages** describing **136 models with 1,811 fields**. The EHI export covers **29 FHIR R4 resource types** — a significant portion but not everything.

**Clearly covered domains:**
- **Demographics**: Patient, RelatedPerson — comprehensive coverage including Canvas-specific extensions for race, ethnicity, sex-at-birth, gender identity, social determinants
- **Clinical problems & conditions**: Condition — full CRUD with clinical/verification status
- **Allergies**: AllergyIntolerance — including reaction severity and manifestation
- **Medications**: MedicationRequest, MedicationStatement, MedicationDispense — covers prescriptions, active medications, and dispensing
- **Immunizations**: Immunization — full coverage
- **Lab results**: DiagnosticReport, Observation, Specimen — covers lab results and vitals
- **Clinical notes & encounters**: Encounter, DocumentReference — encounters map to Canvas notes
- **Procedures**: Procedure — basic coverage
- **Care plans & goals**: CarePlan, Goal — included
- **Care teams**: CareTeam — included
- **Devices**: Device — implantable device tracking
- **Billing/Claims**: Claim, Coverage, CoverageEligibilityResponse — Canvas includes billing data in the export, which is notably better than many vendors
- **Communication**: Communication — maps to Canvas messages
- **Consent**: Consent — patient consent records
- **Questionnaires**: QuestionnaireResponse — patient form responses
- **Media**: Media — includes images and attachments
- **Tasks**: Task — includes task management
- **Provenance**: Provenance — data origin tracking
- **Referrals/Orders**: ServiceRequest — covers referrals and service requests

**Domains with potential gaps (internal models without clear FHIR export mapping):**
- **Assessment**: Canvas stores assessments as a distinct data model (18 fields including narrative, ICD-10 codes, background, status). These may be partially captured in Encounter or Condition resources, but the assessment model's narrative structure may lose fidelity.
- **BillingLineItem**: While Claim is in the export, Canvas internally stores billing line items as distinct objects with CPT codes, charges, units, and modifiers linked to notes. The Claim resource may not capture all billing line item detail.
- **ChargeDescriptionMaster / PayorSpecificCharge**: The CDM and payor-specific charge tables are internal billing configuration. While individual patient billing is in Claims, the charge catalog itself is not exported.
- **CompoundMedication**: Canvas tracks compound medications separately. These may or may not be represented in MedicationRequest/MedicationStatement.
- **Letter**: Canvas has a distinct Letter model (8 fields) for patient correspondence. It's unclear whether letters are captured in Communication or DocumentReference.
- **Posting**: Canvas has 10 posting-related models (78 fields) for payment posting, claim payments, adjustments, etc. This detailed revenue cycle data does not appear to have a FHIR resource in the export.
- **Referral**: Canvas has a detailed referral model (53 fields across 3 sub-models) that may be partially represented by ServiceRequest but likely loses internal referral tracking detail.
- **ReasonForVisit**: Distinct from encounter diagnoses. May be captured in Encounter.reason but unclear.
- **Stop Medication Event**: Distinct events for medication discontinuation. May be partially in MedicationStatement/MedicationRequest.

**Domains that are NOT EHI (correctly excluded from export):**
- **Application, Calendar, CanvasUser, Staff, BusinessLine, Facility, Organization, PracticeLocation, ServiceProvider, Team**: These are system configuration and provider-facing records, not patient-facing clinical data.
- **ProtocolCurrent, ProtocolOverride**: Clinical decision support configuration.
- **Command**: Internal charting UI construct.
- **CommonEnumerationType, ValueSets**: Reference data / system configuration.
- **ExternalEvent**: ADT feed events — operational/integration data.
- **LabPartner & LabPartnerTest**: Lab partner configuration, not patient results.
- **BannerAlert**: While these are patient-facing alerts, they represent transient UI state rather than permanent clinical records. Borderline — could be argued either way.
- **DetectedIssue**: Listed in the FHIR API docs (has CRUD endpoints) but NOT listed in the EHI export resource table. This is a gap — DetectedIssues (drug interactions, contraindications) are clinically relevant patient data.

### Export Format & Standards

The export format is **FHIR R4 NDJSON via Bulk Data Access** — a well-established standard. This is a strong format choice because:
- It's machine-readable and well-structured
- FHIR R4 provides rich semantics for healthcare data
- Bulk Data Access is an established pattern for large exports
- NDJSON enables streaming/line-by-line processing

Canvas uses **US Core STU3.1.1** profiles as a baseline for most resources (based on profile references in the API documentation) but extends them with Canvas-specific extensions. This provides reasonable interoperability while accommodating Canvas-specific data.

However, this is fundamentally the **same FHIR API that backs Canvas's (g)(10) certification** for standardized patient access. The question is whether the 29 resources listed for the EHI export represent a broader set than what (g)(10) requires, or whether they're the same set. Comparing to US Core:

**Beyond US Core (additional resources in Canvas EHI export):**
- Claim — billing data, not in US Core
- Communication — not in US Core STU3.1.1
- Consent — not in standard US Core
- Coverage — insurance data, not in standard US Core
- CoverageEligibilityResponse — not in US Core
- Media — not in standard US Core
- QuestionnaireResponse — not in US Core STU3.1.1
- RelatedPerson — not in standard US Core
- ServiceRequest — not in US Core STU3.1.1
- Specimen — not in US Core STU3.1.1
- Task — not in US Core STU3.1.1

This is encouraging — Canvas has included ~11 resource types beyond what US Core / (g)(10) would require, particularly billing (Claim, Coverage, CoverageEligibilityResponse) and operational data (Task, Communication). This suggests Canvas has given genuine thought to (b)(10) scope rather than simply repackaging their (g)(10) API.

That said, some internal data domains (detailed payment postings, compound medications, assessments) don't have clear FHIR R4 resource mappings and may be lost or compressed in the export.

### Documentation Quality

**Strengths:**
- The EHI export page is clear and straightforward — it explains the mechanism, lists the resources, and links to detailed API docs.
- Each of the 29 FHIR resource API pages has rich field-level documentation with types, descriptions, required markers, value options, and Canvas-specific extensions.
- The SDK documentation provides an unusually transparent view of Canvas's internal data model, making coverage assessment possible.
- Total documented fields across all FHIR resources: **3,698 fields across 84 operations**.

**Weaknesses:**
- No sample export files are provided — there's no example of what an actual NDJSON output looks like for a patient.
- No data dictionary mapping between Canvas internal models and FHIR resources — one has to infer how internal data maps to FHIR output.
- No documentation of what happens to data that doesn't fit into FHIR R4 — do Canvas-specific extensions preserve all internal fields?
- The population export requires contacting support, which adds friction for legitimate EHI export requests.
- No explicit (b)(10) framing — the page doesn't mention the regulatory basis or explain how the 29 resources were chosen to satisfy the "all EHI" requirement.

### Structure & Completeness

**Field-level granularity**: Excellent. Every resource has field-by-field documentation including:
- Field name and data type
- Required/optional markers
- Text descriptions
- Supported value sets for coded fields
- Canvas-specific extensions with their URLs and value types
- Nested object structures

**Coded fields**: Well documented with supported value sets (e.g., claim status codes, clinical status codes, verification status codes).

**Relationships**: Documented via FHIR references (e.g., `Patient/id`, `Encounter/id`). Internal Canvas relationships (e.g., note → billing line items) are documented in the SDK but not explicitly in the FHIR export docs.

**Versioning**: Pages show "Last updated" dates (ranging from 2024 to 2025). No formal changelog or version history.

## Obstacles & Dead Ends

- **FHIR metadata endpoint**: The fumage FHIR server requires a specific instance subdomain, so no public CapabilityStatement is accessible for verification.
- **Population export gated by support**: Population-level EHI export (all patients or groups) requires contacting Canvas support rather than being available as a self-service operation. This is a procedural barrier noted in the documentation.
- **No downloadable schema files**: No OpenAPI spec, JSON Schema, or machine-readable profile definitions are provided alongside the documentation. The HTML API documentation is the primary artifact.
