## What Was Found

The entire EHI export documentation consists of a single 19-page PDF document. The document describes four export formats available through the product's "Data Export" screen:

### Export Mechanism
Users access export via **Registration → Data Export → Custom Export**. The interface allows:
- Selecting specific patients or all patients
- Setting date ranges or selecting all dates
- Scheduling exports (one-time or recurring: daily, weekly, monthly, annually)
- Choosing which formats to include: C-CDA files, Excel file, Notes, and Attachments

The document includes a screenshot of the export interface showing these options.

### Export Formats

1. **C-CDA Files** — Clinical summaries exported using USCDI v1 and HL7 CDA R2 Implementation Guide: C-CDA Templates for Clinical Notes R2.1 Companion Guide, Release 2-US Realm, October 2019 standard.

2. **Excel File** — Structured data organized by tabs. The document lists 15 Excel tabs and provides field-level definitions for 15 entities:
   - **Administrative**: Organization, Patient, Practitioner, Location
   - **Clinical**: Encounter, Condition (tab listed but no field definitions), Coverage (tab listed but no field definitions), Procedure, ServiceRequest, FamilyMemberHistory, Immunization, AllergyIntolerance, CarePlan, Observation
   - **Medications**: MedicationAdministration, MedicationRequest, MedicationStatement

3. **Notes** — Patient notes exported as PDF files, grouped into ZIP archives by patient name.

4. **Attachments** — Attached files (images, Excel, Word, PDF) grouped into ZIP archives by patient name.

### Data Dictionary Detail
The Excel format data dictionary documents 15 entities with 224 fields total. Each field specifies:
- Field name
- Description
- Requirement level (Required, Preferred, Optional)
- Data type (string, code, boolean, dateTime, date, integer, decimal, uri, or reference to another entity)
- Value set references where applicable

The document also includes 30 value sets with 256 coded values, covering standard terminologies (HL7 administrative gender, OMB race/ethnicity, SNOMED CT clinical findings, vaccine codes, etc.).

The field naming and entity structure closely mirror FHIR R4 resource definitions (e.g., Encounter, Patient, Observation, MedicationRequest). The entities use FHIR-style field names and reference FHIR value sets. However, the export format is Excel (not FHIR NDJSON or Bundle), so this is a FHIR-influenced flat export rather than a native FHIR export.

## Export Coverage Assessment

### Data Domain Coverage

**Covered (clearly documented in the Excel export):**
- Patient demographics (extensive: 37 fields including race, ethnicity, language, birth sex, gender identity, religious affiliation)
- Encounters
- Conditions/problem lists (tab listed; field definitions not provided but tab is present)
- Coverage/insurance (tab listed; field definitions not provided but tab is present)
- Procedures
- Service requests/orders
- Family member history
- Immunizations
- Allergies/intolerances
- Care plans
- Medications (administration, requests, statements — 3 separate entities)
- Observations (vitals, lab results, clinical observations)
- Clinical notes (exported as PDF files)
- File attachments (images, documents)
- Organization and location information
- Practitioner information

**Missing or not documented:**
- **Billing data** — The product has a full billing/RCM module with claims, superbills, ERA/remittance, payment records, AR aging, EOBs, and electronic patient statements. None of this appears in the export documentation. The "Coverage" tab captures insurance plan information but not billing transactions, claims, payments, or financial records.
- **Scheduling/appointment data** — While not strictly EHI (administrative/operational), the product stores extensive appointment and scheduling data that could be part of the encounter record. Not documented in the export.
- **Patient portal messages and secure communications** — The product supports secure messaging, chat, and patient portal interactions. These are part of the patient record when they document clinical information. Not mentioned in the export.
- **Custom intake forms and assessments** — The product emphasizes customizable intake forms and clinical assessments across 20+ specialties. The export documentation doesn't describe how custom form data is captured — it may be embedded in Observations or clinical notes, but this is not clarified.
- **Telehealth session records** — The product includes telehealth functionality. Session records are not mentioned in the export.
- **Radiology-specific data** — The product includes a full Radiology Information System (RIS) with PACS integration, DICOM management, MQSA tracking, and radiology-specific reporting. None of this specialized data appears in the export documentation.
- **E-prescribing details** — While MedicationRequest captures prescription orders, the detailed EPCS tracking, PDMP/NARX scores, pharmacy routing, and controlled substance audit trail are not documented.
- **Document management** — Beyond the generic "Attachments" format, the document management system (scanned documents, uploaded files, faxes, Direct messages) is not specifically described.

### Export Format & Standards

The export uses a hybrid approach:
- **C-CDA** for clinical summaries (USCDI v1 compliant)
- **Excel** for structured tabular data with FHIR-influenced field definitions
- **PDF** for clinical notes
- **ZIP** for file attachments

This is a reasonable approach for a (b)(10) export — it goes beyond just C-CDA by including structured Excel data and raw document files. However, the Excel format has limitations:
- **No explicit relationship keys** — While entities reference each other (e.g., Observation references Encounter, Patient), the documentation doesn't describe how these references are expressed in the Excel tabs (foreign key columns? identifiers? tab cross-references?).
- **No schema file** — There's no machine-readable schema (XSD, JSON Schema, etc.). The data dictionary is only in PDF prose.
- **The C-CDA component is USCDI v1** — This covers the standard clinical data subset but not the billing, specialty, or operational data that should be in a (b)(10) export.

A third party could reconstruct a reasonable clinical picture from this export but would struggle with:
1. Understanding relationships between Excel tabs without explicit foreign key documentation
2. Importing billing/financial data (not included)
3. Handling specialty-specific clinical data from radiology, behavioral health, or other modules

### Documentation Quality

The documentation is **minimally adequate** but has notable weaknesses:

**Strengths:**
- Field-level definitions for 15 entities with data types and requirement levels
- Value set definitions for coded fields
- Clear step-by-step export instructions with a screenshot
- Multiple export format options

**Weaknesses:**
- The landing page has a broken WordPress shortcode (`[embeddoc]`) visible to users, suggesting limited maintenance attention
- The PDF is dated November 2023 and titled "2023" — it hasn't been updated in over 2 years despite being the sole documentation for a certified product
- "Condition" and "Coverage" are listed as Excel tabs but have no field-level definitions in the data dictionary
- No sample export files or worked examples
- No documentation of how entity relationships are expressed across Excel tabs
- No versioning or change history

### Structure & Completeness

The data dictionary is moderately granular:
- **Entity names**: Yes (15 documented)
- **Field names**: Yes (224 fields)
- **Data types**: Yes (string, code, boolean, dateTime, etc.)
- **Descriptions**: Yes (brief but present for each field)
- **Cardinality/requirement**: Yes (Required/Preferred/Optional)
- **Value sets**: Yes (30 value sets with coded values)
- **Relationships**: Partially (references to other entities noted but not formalized)
- **Examples/samples**: No
- **Schema files**: No

### Overall Assessment

EnableDoc's EHI export documentation represents a genuine effort to provide a (b)(10) export mechanism that goes beyond the USCDI/FHIR clinical summary. The multi-format approach (C-CDA + Excel + Notes + Attachments) is practical and covers more ground than vendors who simply point to their FHIR API.

However, there is a significant **billing data gap**. The product is marketed as an all-in-one EHR/PMS/billing platform with features including claims submission, ERA processing, payment reconciliation, AR aging, and superbill management. None of this billing/financial data appears in the export documentation. For a product where billing is a core function, this is a meaningful omission from the designated record set.

The **radiology-specific data gap** is also notable. The product includes a full RIS module with PACS integration, DICOM management, and MQSA tracking. This specialty clinical data used for patient care decisions is part of EHI but isn't addressed in the export.

The documentation itself is a single PDF that appears to have been created in late 2023 and not subsequently maintained. The broken WordPress shortcode on the landing page and the 404 URL on the ONC disclosure page suggest limited ongoing attention to this compliance area.
