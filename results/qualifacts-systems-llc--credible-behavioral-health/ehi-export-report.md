## What Was Found

### Export Process
Qualifacts provides two export types for Credible:

1. **Single Patient Export**: Initiated by designated agency staff within the Credible application after a patient or authorized representative requests it from their provider. Requests enter a processing queue.
2. **Patient Population Export**: Requested by submitting a ticket through the Qualifacts Care Center. Qualifacts staff initiate the process. May take up to 30 calendar days. Only one can be requested at a time. Requires agreement to Terms of Use.

Completed exports are accessed via the **Report Inbox** on the Reports tab within Credible. Download links expire after 30 calendar days.

### Export Format
The export is a **ZIP file containing Newline Delimited JSON (NDJSON) files**. Each JSON file represents a data class (entity), with the naming convention `Content{EntityName}.json`. For example:
- `ContentClaims.json` — claims data
- `ContentAllergies.json` — allergy records
- `ContentVisitService.json` — visit/service records
- `ContentClientProfile_Custom.json` — custom profile fields

**Attachments** (documents, images) are included in their original uploaded file format with GUID filenames that map to records in `ContentClientAttachments.json`. For partner agencies using their own file storage, the file path is provided but the actual file must be obtained from the partner.

## Export Coverage Assessment

### Data Domain Coverage

This is a genuinely comprehensive (b)(10) export that goes well beyond USCDI/US Core clinical summaries. The export covers:

**Clearly Covered:**
- **Demographics & contacts**: Profile, Profile Extended, Profile Previous Address/FullName, Contact, Family
- **Diagnoses**: Client Diagnosis, Diagnosis Detail, Visit Service Diagnosis (3 separate entities with 92 combined fields)
- **Medications & prescribing**: Medication Request, Medication History, EMAR, eRx Messages (10 entities, 293 fields — very thorough)
- **Allergies**: 16-field entity with severity, reaction, onset date, etc.
- **Lab results**: Lab Report and Lab Test Results (47 combined fields)
- **Immunizations**: Covered (5 fields)
- **Clinical notes & documentation**: Clinical Notes, Notes, Credible Plan Documentation
- **Treatment planning**: Treatment Plan, Treatment Plan Plus (with Details and Extended), Credible Plan (Header, Component, Custom Extended, Documentation, Signature) — 9 entities dedicated to treatment planning, reflecting the behavioral health focus
- **Behavioral health assessments**: ASAM Assessment, Questionnaire, Questionnaire Category, Outcomes
- **Billing & claims**: Claims, Payments, Payment Plan, Liability (164 fields!), Statement Header/Detail, 277 Response — this is extensive billing coverage
- **Insurance/enrollment**: Insurance (50 fields), Insurance Subscriber, Eligibility, Enrollment, Payer, Insurance Visit Type
- **Authorization**: Authorization, Authorization Provider, Authorization Visit Type, Medication Prior Authorization
- **Visit/service records**: Visit Service (97 fields), Visit Service Approval, Visit Service Claim Note, Visit Service Diagnosis, Visit Service Insurance, Visit Service Transportation
- **Residential/inpatient**: Bed Board Billing, Bed Board Shift Notes, Bed Board Whiteboard Notes, Foster Home
- **Attachments**: ContentClientAttachments with GUID mapping to actual files
- **Care coordination**: Care Team, Care Plan, Direct Sent/Received Messages
- **Family medical history**: Family Medical History, Family Medical History Detail (66 combined fields)
- **Implantable devices**: 20-field entity
- **Scheduling**: Scheduler Appointment, Scheduler Planner
- **Custom agency-specific data**: Through custom fields on Profile, Episode, Medical Profile, Visit Service, Employee

**Potential gaps (minor):**
- **Vital signs**: No dedicated "Vitals" entity is documented. Vitals may be captured within Visit Service custom fields or Questionnaire data, but there's no explicit vitals entity. For a behavioral health system, this is a minor gap — vitals are tracked less frequently than in primary care.
- **Telehealth session records**: No explicit telehealth entity, though Qualifacts added OnCall Health for telehealth. These may be captured as Visit Service records.
- **AI-generated content**: Qualifacts iQ (AI note generation) content may be captured in Clinical Notes, but there's no explicit entity for AI transcripts or generated content.

### Export Format & Standards

The export is a proprietary **NDJSON-based format** with human-readable field names. Each entity maps to a JSON file. This is not a recognized standard (not FHIR, C-CDA, or HL7 v2), but it's well-documented and structured.

**Strengths of the format:**
- Human-readable field names (e.g., "Insurance Policy Number", not cryptic codes)
- JSON is widely parseable
- Each data class in its own file enables incremental processing
- Attachment files are included with GUID-based mapping
- Custom fields are included per agency configuration

**Weaknesses:**
- Relationships between entities rely on shared ID fields (Client Id, Visit Id, Claim Id, etc.) but there's no explicit relationship documentation or foreign key map
- No formal schema (no JSON Schema, no OpenAPI spec) — just the data dictionary
- Date format inconsistency: some fields use "2023-09-06T10:54:00", others use "5/3/2021 2:18:00 PM"
- No explicit documentation of value sets for coded fields (e.g., what are the valid values for "Current Status" in Claims?)
- The description field often just restates the field name (e.g., field "Batch Date" described as "Batch Date") rather than explaining semantics

**Could a third party reconstruct the patient record?** Mostly yes. The field names are descriptive enough that a competent developer could import the data. The main challenges would be:
1. Understanding the relationships between entities (e.g., how Visit Service relates to Claims)
2. Interpreting coded fields without value set documentation
3. Handling the mixed date formats
