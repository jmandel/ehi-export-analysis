## What Was Found

### Export Format

The EHI export documentation for Sunrise is a **complete database schema data dictionary** delivered as a static HTML site generated by a tool called "WebER" (Web Entity-Relationship Diagram). The export itself is a **SQL-level database extract** — the documentation describes every table and column in the Sunrise database that is included in the EHI export.

This is a genuine (b)(10) implementation. The export is not FHIR, not C-CDA, not a clinical summary — it is a raw database schema documentation covering the full Sunrise data model. The vendor explicitly labels it as "170.315 (b)(10) EHI Export."

### Content Structure

The PR38 (latest) archive contains 4 database schemas:

| Schema | Full Name | Tables | Description |
|--------|-----------|--------|-------------|
| **SCM** | Sunrise Clinical Manager | 2,728 | Core clinical and operational database |
| **MNC** | Medical Necessity Checking | 11 | Medical necessity / ABN configuration |
| **IMG** | Imaging | 7 | Document imaging and binary object storage |
| **FS** | Financial System | 1 | EHI-specific view into imaging file storage |

**Total: 2,747 tables with 42,849 documented columns.**

Each table page includes:
- Fully qualified name (dbo.TableName)
- Table definition/description
- Complete column listing with:
  - Column name
  - Data type (SQL Server types: int, varchar, bigint, datetimeoffset, etc.)
  - Nullable flag (YES/NO)
  - Column definition (often detailed, explaining business meaning)
  - Domain reference where applicable
- Primary and unique key constraints

## Export Coverage Assessment

### Data Domain Coverage

**Strongly covered domains (many tables, detailed column definitions):**

- **Demographics & Patient Data** (~74 tables): CV3Person, CV3PersonName, CV3Address, CV3AddressType, plus extensive ADT/registration tables. Includes patient identifiers, contacts, insurance, and relationships.
- **Medications & Pharmacy** (~154 tables): Comprehensive drug catalog, dosing, dispensing, administration records (BCMA), medication reconciliation, and e-prescribing data. Covers the full medication lifecycle.
- **Orders** (~109 tables): CPOE orders, order routes, order policies, order reconciliation, ancillary orders. Deeply documented.
- **Billing & Revenue Cycle** (~275 tables): The largest single domain. Claims, charges, payments, adjustments, denials, appeals, fee schedules, payer configurations, ERA transactions, SuperBill data. This is a major strength — many vendors' (b)(10) exports omit billing data entirely.
- **Clinical Documentation** (~95 tables): Chart documentation, notes, annotations, flowsheets, clinical document events.
- **Lab & Results** (~73 tables): Specimen types, observations, results, lab integration data.
- **Registration & ADT** (~93 tables): Admissions, discharges, transfers, visit types, encounter management.
- **Surgery & Perioperative** (~41 tables): Surgical items, case indicators, anesthesia, perioperative records.
- **Scheduling** (~45 tables): Appointments, booking, scheduling templates.
- **Allergy** (27 tables): Allergens, allergy declarations, criticality, severity levels, reactions.
- **Problem Lists & Diagnoses** (~32 tables): ICD codes, diagnosis lists, health issues.
- **Immunizations** (~16 tables): Vaccine data, immunization registries, VFC eligibility.
- **Imaging & Documents** (8 tables): Document types, binary objects (stored images/scans), document type sets.
- **Care Providers** (~28 tables): Provider identifiers, roles, visit assignments.

**Present but less granularly documented:**

- **Vital Signs**: Only 2 tables directly named for vitals, though vital sign observations may be stored in the generic observation (CV3BasicObservation) and flowsheet tables.
- **Care Plans / Goals**: Not prominently visible as distinct tables, but may be captured within clinical documentation structures.

**Not included (appropriately excluded — these are not EHI):**

- Audit logs are present in a small number of tables (~13 security/audit tables) but these are operational, not clinical.
- System configuration tables appear minimal — the export focuses on patient-facing data.

### (b)(10) vs (g)(10) Assessment

**This is a genuine (b)(10) implementation.** There is no conflation with FHIR or (g)(10):

- The export is a SQL database schema dump, not FHIR resources
- It covers 2,747 tables across clinical, financial, imaging, and administrative domains
- Billing/revenue cycle data (275 tables) is extensively documented — this is data that no FHIR-based export would cover
- Surgery, scheduling, radiology, pharmacy, and other specialty data are all included
- The documentation predates and is independent of any FHIR API documentation

This is one of the more comprehensive (b)(10) implementations encountered. The vendor has clearly documented the actual database schema rather than simply pointing to their FHIR API.

### Export Format & Standards

- **Format**: SQL Server database export. The documentation describes SQL Server table schemas (dbo schema, SQL Server data types like `datetimeoffset`, `uniqueidentifier`, `nvarchar`, `varbinary(max)`, `bit`).
- **Standard**: Proprietary vendor schema — not FHIR, C-CDA, or any external standard. This is appropriate for a (b)(10) export that covers the full database.
- **Relationships**: Foreign key relationships are not explicitly documented in the HTML files (the relationship pages are empty). However, column definitions frequently reference other tables (e.g., "Refer to the ElementID column in the SXAIMGElement table"). Table naming conventions and column naming patterns (e.g., suffixed with "ID", "XRef" tables) make relationships inferrable.
- **Reconstructability**: A third party could reconstruct the patient record from this export given the documentation, though the lack of explicit FK relationships and the sheer number of tables (2,747) would require significant domain expertise. The column-level definitions are generally helpful — many include business context, not just technical descriptions.

### Documentation Quality

**Strengths:**
- **Completeness**: 2,747 tables with 42,849 columns — this is exhaustive
- **Consistency**: Every table follows the same template: name, definition, columns with types and definitions
- **Column-level documentation**: Most columns have meaningful business definitions (e.g., "Identifies the build number and patch level of the software" rather than just "int")
- **Active maintenance**: 5 versions over ~18 months shows ongoing attention
- **Expanding scope**: PR38 added 3 new schemas (FS, IMG, MNC) not in earlier versions
- **Honest approach**: The vendor documents the actual database schema, not a sanitized summary

**Weaknesses:**
- **No export procedure documentation**: The HTML data dictionary describes the schema but there is no user guide, export instructions, or screenshots showing how to actually perform the export. The page says "Click on the index.html file in the extracted files folder to view the EHI Export definition" but provides no workflow documentation.
- **No sample data**: No example export files, sample records, or test data are provided
- **No relationship diagrams**: The ER diagram tool was used, but relationship data is empty — no FK constraints are documented. This makes it harder to navigate the 2,747-table schema.
- **No value set documentation**: Coded fields reference domain tables (e.g., CV3AllergyConfLevel, CV3AmbulatoryStatus) but the valid codes/values are not enumerated in the documentation.
- **Version mismatch**: Documentation is for version 22.1 (with patch releases) but the certified product is version 25.1. The documentation may not reflect schema changes in versions 23.x through 25.1.
- **No format specification**: The documentation describes the schema but doesn't specify the actual export file format (CSV? SQL dump? Proprietary binary?).

### Structure & Completeness

- **Granularity**: Field-level documentation with data types, nullable flags, PK constraints, and definitions. This is among the most granular EHI export documentation available.
- **Value sets**: Referenced but not enumerated. Domain tables exist (e.g., CV3AllergyConfLevel) but their valid values are not listed.
- **Relationships**: Not explicitly documented despite using an ER diagram tool. Column definitions provide implicit references.
- **Versioning**: Clear version progression (PR23→PR38) with dates, but no change log between versions.
