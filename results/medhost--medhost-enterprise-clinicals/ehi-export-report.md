## What Was Found

### Export Format

MEDHOST's EHI export produces **NDJSON files** structured according to **FHIR R4 v4.0.1**. Multiple NDJSON files are generated per patient, delivered as a compressed ZIP file. The export supports two modes:

1. **Single patient export**: Initiated by the patient via the YourCare® Universe patient portal, or by a facility administrator on the patient's behalf. The resulting export is delivered via a secure email link.
2. **System export**: Initiated by a facility administrator. Presumably exports data for multiple/all patients.

### Extension Fields Documentation (XLSX)

The primary technical artifact is `MEDHOST-FHIR-Extension-Fields.xlsx`, a 45-sheet Excel workbook documenting MEDHOST's custom FHIR extensions. Key characteristics:

- **43 data sheets** (excluding the MEDHOST info sheet and a reference sheet)
- **743 total extension fields** across the documented resources
- **28 unique FHIR resource types** covered
- Each field is documented with: Field Name, Version, FHIR Field Type, Max Field Length, Field Description, and database table/column mappings for three systems (Enterprise, EDIS, and "Y" — likely YourCare)

**FHIR Resource Types documented:**
AllergyIntolerance, Appointment, CarePlan, ChargeItem, Condition, Consent, Coverage, DetectedIssue, Device (Implantable), DiagnosticReport, Encounter, FamilyMemberHistory, Goal, Immunization, Location, MedicationAdministration, MedicationRequest (3 variants: Discharge Med, Inpatient Med, Prescriptions), MedicationStatement, Observation (10 variants including Labs, Vitals, Social History subtypes), Patient, Practitioner, Problem, Procedure, QuestionnaireResponse, RelatedPerson, ServiceRequest

### What the documentation tells us

The extension fields document reveals that MEDHOST captures data beyond standard FHIR R4 fields. For example:
- **Patient**: SSN alpha prefix, religion, congregation, and other demographic extensions
- **Encounter**: Confidential flag, legal hold flag
- **AllergyIntolerance**: Pharmacy reviewed status, allergy type
- **ChargeItem**: Present as a documented resource — this is notable because it indicates billing-adjacent data is included in the export

The database column mappings (e.g., `PATHIST.SSNAL`, `mreroir.erconflg`, `clalgdttb.cadcmnt`) provide internal schema visibility, referencing tables in the Enterprise MSSQL database and the EDIS system.

## Export Coverage Assessment

### Data Domain Coverage

**Clearly covered domains** (documented via FHIR resource types with extension fields):
- Demographics (Patient with extensive extensions)
- Allergies (AllergyIntolerance)
- Conditions/Problems (Condition, Problem — two separate sheets)
- Medications (MedicationAdministration, MedicationRequest for discharge/inpatient/prescriptions, MedicationStatement for home meds)
- Lab results (Observation Labs, DiagnosticReport)
- Vitals (presumably in Observation, though the extension sheet focuses on social history subtypes)
- Immunizations (Immunization)
- Procedures (Procedure, Past Procedure)
- Encounters (Encounter with extensions)
- Care Plans (CarePlan for Discharge Plan)
- Goals (Goal)
- Family History (FamilyMemberHistory)
- Consent records (Consent)
- Coverage/Insurance (Coverage)
- Implantable Devices (Device)
- Appointments (Appointment)
- Social History observations (Alcohol Use, Drug Use, Education, Marital Status, Occupation, Sexual Behavior, Travel, Smoking Status)
- Questionnaire Responses (QuestionAnswer)
- Related Persons (RelatedPerson)
- MDRO (Multi-Drug Resistant Organism tracking)
- Detected Issues (DetectedIssue — drug interaction alerts)

**Partially covered or ambiguous:**
- **Charge data**: ChargeItem is documented with extension fields, suggesting billing charge data is included. However, it's unclear whether full billing records (claims, payments, adjustments) are covered — ChargeItem captures individual charges but not the complete revenue cycle.
- **Clinical notes**: No DocumentReference or Composition resource is documented in the extension fields XLSX. The product stores extensive clinical notes (physician notes, nurse charting, discharge summaries, H&P), but it's unclear whether these are exported as FHIR DocumentReference resources (with no extensions needed) or are missing from the export.
- **Orders**: ServiceRequest covers "Ancillary Orders" and "PC Orders," but it's unclear whether all CPOE order types are captured.

**Likely missing or not documented:**
- **Imaging data**: No ImagingStudy or Media resource documented. The product integrates with radiology systems but it's unclear if actual images (DICOM, etc.) are included.
- **Full billing/claims data**: While ChargeItem is present, there's no Claim, ClaimResponse, ExplanationOfBenefit, or Invoice resource. However, this may be by design — the Clinicals product's certification is separate from Financials, and full billing data may reside in the separately certified MEDHOST Enterprise - Financials product.
- **Clinical notes detail**: No explicit documentation of how narrative clinical documentation is exported. This is a significant gap for a product that stores extensive physician and nursing notes.
- **Perioperative/Anesthesia records**: The product has dedicated perioperative and anesthesia modules, but no specific FHIR resources or extensions are documented for surgical/anesthesia data beyond basic Procedure.
- **Patient portal messages/communications**: No Communication resource documented.
- **Documents/attachments**: No DocumentReference resource documented.

### Export Format & Standards

- **Format**: FHIR R4 v4.0.1 NDJSON files in a ZIP archive
- **Standard**: Based on FHIR R4, with vendor-specific extensions documented in the XLSX
- **Appropriateness**: Using FHIR NDJSON is a reasonable format choice. The extension mechanism allows MEDHOST to include data beyond US Core / USCDI requirements while maintaining a standard structure.

**Critical question — is this truly b(10) or repackaged g(10)?**

MEDHOST's approach shows signs of genuine b(10) effort rather than just repackaged g(10):
1. **Extension fields**: The 743 extension fields across 43 resource sheets demonstrate data beyond USCDI/US Core. Fields like SSN alpha prefix, religion, pharmacy review status, confidential flags, and legal hold flags go well beyond what g(10) requires.
2. **ChargeItem**: Including billing charge data is a b(10) indicator — g(10) doesn't require financial data.
3. **Database column mappings**: The XLSX includes internal database table/column references, showing they've traced data from their internal schema to FHIR resources.
4. **Multiple observation subtypes**: Documenting 10+ Observation variants (alcohol use, drug use, education, marital status, etc.) goes beyond standard USCDI social history requirements.

However, there are concerns:
- No documentation of how **clinical notes** are exported — a major data domain for an inpatient EHR
- No **DocumentReference** resource for documents and attachments
- No documentation of **perioperative/surgical/anesthesia** data export, despite these being major product modules
- The XLSX only documents **extension fields** — it doesn't provide a complete data dictionary of all exported fields (base FHIR fields + extensions). You'd need to understand standard FHIR R4 resources to know the complete export schema.

### Documentation Quality

- **Readability**: The documentation is minimal — a brief paragraph on the interoperability page plus an Excel spreadsheet. There are no user guides, no step-by-step export instructions, no screenshots of the export interface, and no sample export files.
- **Data dictionary**: The XLSX provides field-level documentation for extension fields only, not a complete data dictionary. Each field has a name, type, max length, and description, plus internal database mappings. Descriptions vary in detail — some are just the field name restated, others provide meaningful context.
- **Developer usability**: A developer attempting to import MEDHOST EHI exports would need to: (1) understand FHIR R4 base resources, (2) understand the extension structure from the XLSX, and (3) figure out which NDJSON files correspond to which resources — none of this is documented. No sample files are provided.
- **Maintenance**: The extension fields include a "Version" column (all currently showing version 1), suggesting versioning is planned. No change history is available.

### Structure & Completeness

- **Granularity**: Field-level documentation with data types and max lengths — reasonable for extension fields
- **Value sets**: Not documented. Coded fields (e.g., allergy type, religion) don't include allowed values.
- **Relationships**: Not explicitly documented beyond what FHIR R4 provides by default (references between resources)
- **Missing**: No documentation of which FHIR resources (beyond those with extensions) are included in the export, no sample data, no schema validation artifacts (e.g., StructureDefinitions for the custom profiles)
