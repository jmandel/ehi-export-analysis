## What Was Found

### EHI Export Format

The EHI export produces a **ZIP file** containing two files per patient:

1. **`.json` file**: A FHIR R4 Bundle containing all resources on record for the patient. The documentation lists 17 FHIR resource types that "may be included":
   - AllergyIntolerance, CareTeam, Communication, Condition (listed twice — likely a typo), Consent, Device, DiagnosticReport, DocumentReference, Encounter, Goal, Immunization, MedicationRequest, Observation, Patient, Procedure, ServiceRequest

2. **`.xml` file**: A C-CDA v2.1 Patient Continuity of Care Document with 18 sections:
   - Allergies, Assessment and Plan, Care Team, Encounters, Family History, Goals, Health Concerns, Immunizations, Medical Equipment, Medications, Notes, Patient, Plan of Treatment, Problems, Procedures, Results, Social History, Vital Signs

The export supports single patient or multiple patients. No API documentation is provided for how the export is triggered — the page describes only the output format.

### FHIR Resource Documentation (Field-Level Detail)

The FHIR section of the site provides detailed field-level documentation for 22 resource types. Each resource page has a table with:
- **Field Name** (including dotted sub-paths like `.coding.system`)
- **Field Type** (Text, code, CodeableConcept, Reference, etc.)
- **Cardinality** (0..1, 1..1, 0..*, etc.)
- **Description and bindings** (including value set bindings and One Medical-specific notes)

The 22 documented resource types with field counts:
- Patient (60 fields, 2 tables including extensions), Observation (48 fields), DocumentReference (42 fields), Immunization (36 fields), DiagnosticReport (35 fields), Procedure (34 fields), Encounter (33 fields), Coverage (31 fields), Questionnaire (31 fields), ServiceRequest (30 fields), AllergyIntolerance (27 fields), CareTeam (26 fields), Location (26 fields), CarePlan (24 fields), Condition (23 fields), QuestionnaireResponse (23 fields), MedicationRequest (21 fields), Practitioner (19 fields), Organization (18 fields), Provenance (17 fields), Medication (13 fields), Device (12 fields)

**Notable: The EHI export page lists resources not documented in the FHIR section**: Communication, Consent, and Goal have no individual resource documentation pages. Conversely, the FHIR section documents resources not listed on the EHI export page: CarePlan, Coverage, Location, Medication, Organization, Practitioner, Provenance, Questionnaire, QuestionnaireResponse. These are likely referenced/supporting resources in the FHIR bundle.

### C-CDA API Documentation

The C-CDA section documents a separate API endpoint for generating Continuity of Care Documents:
- **Endpoint**: `GET https://production.app.1life.com/api/ccda`
- **Authentication**: Basic Auth (registration with 1Life required)
- **Parameters**: `patient_id` (required), `start_date` (optional), `end_date` (optional)
- Some C-CDA sections respect date range filtering; others always return all data

### Extensions

One Medical documents 11 FHIR extensions:
- **US Core**: Race and Ethnicity (on Patient resource)
- **Machine Learning**: A complex extension with sub-extensions (source type, model name, model repository, model type, model use case, model performance, prediction characteristics) — used on Observation and Procedure resources. Resources with ML extensions are noted as not authoritative and typically have preliminary/draft status.
- **First Party Data**: Used on Procedure resources

The ML extensions use URLs pointing to One Medical's internal Google Sites knowledge base (not publicly accessible).

### Custom Terminology

One Medical defines 3 custom codes under `http://onemedical.com/terminology`:
- **Consent.TOS**: Terms of Service consent form (signed by new members)
- **Communication.TMN**: Treat Me Now — secure message threads from on-demand visits
- **Communication.AVS**: After Visit Summary — post-encounter follow-up instructions

### FHIR API Infrastructure

- Root URLs: `https://api.prod.1life.com/fhir/4.0` (1Life Production), `https://api.stage.1life.com/fhir/4.0` (Testing), and a Chirp/HealthLake URL
- Media type: `application/fhir+json`
- CapabilityStatement available at `GET /4.0/metadata`
- Extensions search parameter supported: `extension=[url]`

## Export Coverage Assessment

### Data Domain Coverage

The EHI export uses FHIR R4 as its format. The FHIR resource types included broadly map to **standard clinical data domains** well:

**Clearly covered domains:**
- Demographics (Patient)
- Conditions/Problem lists (Condition)
- Medications/Prescriptions (MedicationRequest, Medication)
- Allergies (AllergyIntolerance)
- Lab results (DiagnosticReport, Observation)
- Vital signs (Observation)
- Immunizations (Immunization)
- Procedures (Procedure)
- Encounters/Visits (Encounter)
- Care plans and goals (CarePlan, Goal, CareTeam)
- Clinical notes/documents (DocumentReference)
- Devices/Implants (Device)
- Referrals (ServiceRequest)
- Insurance/Coverage (Coverage)
- Consent records (Consent)
- Questionnaire responses (Questionnaire, QuestionnaireResponse) — this is notable as it could capture custom screening forms and assessments
- Secure messaging/communications (Communication) — includes Treat Me Now and After Visit Summary threads

**Domains with unclear or missing coverage:**
- **Billing data**: No mention of billing records, charges, claims, or payment information. Coverage (insurance) is documented, but actual billing transactions (charges, claim submissions, EOBs) are absent. For a primary care practice that bills insurance for every visit, this is a significant gap in the EHI export.
- **Family health history**: Listed in the C-CDA sections but not as a FHIR resource type. It may be embedded in Observation or another resource, but there's no explicit documentation.
- **Social history**: Listed in C-CDA sections but only "Social History (Smoking Status)" is mentioned. Broader social determinants of health are not explicitly documented.
- **Patient-provider messaging content**: Communication resource is listed, which is good. However, the documentation for Communication has no individual resource page, so the granularity of what's exported (full message threads? just metadata?) is unclear.
- **Virtual visit / telehealth records**: Not explicitly mentioned. Presumably captured as Encounters with a virtual visit type, but not documented.
- **Photos/attachments from virtual visits**: May be in DocumentReference, but not explicitly described.
- **Chronic care management data** (Impact by One Medical): Care plans and goals are present, which may cover this, but care navigator notes and coaching records are not explicitly mentioned.

### The (b)(10) vs (g)(10) Question

This is a **critical finding**: The EHI export documentation is essentially a thin wrapper around One Medical's FHIR API documentation. The resource types listed on the EHI export page (17 types) are a subset of the FHIR API resource types documented in detail (22 types). The FHIR API documentation itself is clearly the (g)(10) API documentation — it describes authentication, search parameters, pagination, and all the standard US Core resources.

However, One Medical's approach is more thoughtful than a simple "our FHIR API is our EHI export" conflation:

1. **The EHI export includes non-US Core resources**: Communication, Consent, Goal, Questionnaire, and QuestionnaireResponse go beyond the standard US Core/USCDI scope. This suggests One Medical has thought about what additional data to include.
2. **The export produces a complete FHIR bundle per patient** — not a query-by-query API, but a single downloadable file.
3. **The C-CDA complement adds sections** (Family History, Social History, Notes) that provide additional clinical context.

That said, the export still fundamentally operates within the FHIR data model, which means **any data that doesn't map cleanly to FHIR resources is likely missing**. For a proprietary EHR built from scratch, there is almost certainly internal data (billing transactions, internal task queues for care navigation, membership data, referral tracking details) that has no natural FHIR representation and appears absent from the export.

### Export Format & Standards

- **Format**: FHIR R4 JSON Bundle + C-CDA v2.1 XML, delivered as a ZIP
- **Standards compliance**: The JSON uses FHIR R4 with US Core profiles. The XML uses C-CDA v2.1.
- **Appropriateness**: FHIR R4 is appropriate for the clinical data this primary care platform manages. The dual-format approach (FHIR + C-CDA) provides both machine-readable structure and a standardized clinical document format.
- **Reconstructability**: A third party could reconstruct most of the clinical patient record from this export. The detailed field-level documentation (629 fields across 22 resources) provides sufficient schema information. However, relationships between resources rely on FHIR reference mechanics, which are standard but require FHIR expertise to navigate. The absence of billing data means the financial record cannot be reconstructed.

### Documentation Quality

**Strengths:**
- The documentation is well-organized in a clean Hugo-based doc portal
- Field-level detail is thorough: every resource has a table with field name, type, cardinality, and description
- Custom extensions and terminology are explicitly documented
- The C-CDA API has clear endpoint documentation with parameters and response codes
- 629 total fields documented across 22 resource types is substantial

**Weaknesses:**
- **No sample export files**: There are no example FHIR bundles or C-CDA documents. A developer implementing an import would have to construct expected outputs from the field tables alone.
- **No export trigger documentation**: The EHI export page describes the output format but says nothing about how to request or trigger an export. Is it an API call? A button in the UI? A request to support? This is a significant omission.
- **Three resource types undocumented**: Communication, Consent, and Goal are listed as EHI export resource types but have no documentation pages.
- **No value set documentation for coded fields**: While the Terminology page documents 3 custom codes, many fields reference standard terminologies (SNOMED, LOINC, ICD-10) without specifying which value sets or which codes One Medical actually uses.
- **Machine learning extension URLs point to internal Google Sites**: The extension URLs (`sites.google.com/onemedical.com/...`) are not publicly accessible, so the full extension specifications cannot be verified externally.

### Structure & Completeness

- **Granularity**: Good — field names, data types, cardinality, and descriptions for most fields
- **Value sets**: Partially documented. Custom codes have a dedicated Terminology page, but standard code system bindings are mentioned in descriptions without specifying allowed values
- **Relationships**: Implicit via FHIR references (e.g., Encounter references Patient, Observation references Encounter). The reference targets are documented in field descriptions.
- **Versioning**: No change history or versioning visible in the documentation. The site's `Last-Modified` header shows `2026-02-12`, so it was recently updated.
- **Condition listed twice**: The EHI export overview lists "Condition" twice in the FHIR resource types table — this appears to be a documentation error.
